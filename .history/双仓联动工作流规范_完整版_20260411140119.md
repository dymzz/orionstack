# OrionStack 双仓联动工作流规范

本文档为完整规范。当前 Phase 1 默认执行轻量模式，日常以 kb.ps1 为入口；仅在涉及边界、API、工作流、设计方案变化时，才按本文档执行扩展同步。


> 文档版本：v0.1  
> 适用范围：`orionstack`（主工程仓） + `orionstack-kb`（工程知识库仓）  
> 文档状态：执行规范草案

---

## 1. 文档目标

本文档用于规范 `orionstack` 主工程仓与 `orionstack-kb` 知识库仓之间的联动更新方式，解决以下问题：

1. 如何避免代码与知识文档长期脱节
2. 如何让知识库仓持续作为 AI 开发入口有效工作
3. 如何在不增加过多维护负担的前提下，保持双仓同步
4. 如何区分“必须同步更新”和“可延后更新”的内容

本文档的核心目标不是追求形式化流程本身，而是保证：

- 主工程仓保持干净
- 知识库仓保持可读、可检索、可作为 AI 上下文入口
- 核心架构、阶段边界、接口约定不会快速腐坏

---

## 2. 双仓职责定义

### 2.1 主工程仓 `orionstack`

主工程仓用于承载：

- 前后端代码
- 配置
- 测试
- 部署文件
- 运行说明
- 少量必要文档

主工程仓的核心职责是：

**可运行、可测试、可交付。**

### 2.2 知识库仓 `orionstack-kb`

知识库仓用于承载：

- 架构设计文档
- 产品边界文档
- API 契约草案 / 冻结稿
- 工作流说明
- ADR 决策记录
- 路线图
- 主工程目录地图
- repomix 产物
- AI 开发入口文件

知识库仓的核心职责是：

**可理解、可检索、可追溯、可作为 AI 开发入口。**

## 3. 联动更新总原则

### 3.1 代码优先落地，知识随后同步

双仓协作中，允许代码先行，但不允许长期不同步。

原则如下：

- 可以先完成最小代码修改
- 但核心变更必须在同一开发批次内同步到知识库仓
- 不允许“代码已大改，知识库完全没更新”

### 3.2 只同步高价值知识，不同步所有细节

知识库仓不负责记录所有实现细枝末节，只记录：

- 会影响理解项目方向的内容
- 会影响后续开发边界的内容
- 会影响 AI 开发判断的内容
- 会影响多文件协作的内容

### 3.3 冻结约束必须优先维护

所有会影响项目方向判断的内容，优先同步到：

- `context/project_index.md`
- `context/current_phase.md`
- `context/frozen_contracts.md`
- `context/ai_entry.md`

这是双仓联动中的最高优先级区域。

### 3.4 不为同步而同步

如果只是：

- 小范围重命名
- 注释调整
- 非关键实现优化
- 不影响边界的内部重构

可以不立即更新知识库仓，只需在阶段性整理时补充。

## 4. 哪些变更必须联动更新

以下变更发生时，必须更新知识库仓。

### 4.1 项目定位变化

例如：

- 产品定位变化
- 首个场景变化
- 技术主栈变化
- 路线图优先级变化

必须更新：

- `context/project_index.md`
- `context/frozen_contracts.md`
- `docs/architecture/orionstack_overview.md`
- `docs/product/product_positioning.md`

### 4.2 首期范围变化

例如：

- MVP 范围扩大或收缩
- 新增一个必须支持的能力
- 明确放弃某个原计划能力

必须更新：

- `context/current_phase.md`
- `context/frozen_contracts.md`
- `docs/product/mvp_scope.md`

### 4.3 模块边界变化

例如：

- FastAPI / LangGraph / LlamaIndex 职责变化
- 新增核心模块
- 原模块被拆分或合并

必须更新：

- `docs/architecture/module_boundaries.md`
- `docs/architecture/system_layers.md`
- `docs/engineering/repo_map.md`

### 4.4 API 契约变化

例如：

- 新增核心接口
- 请求 / 响应字段变化
- 错误模型变化

必须更新：

- `docs/api/api_contract_draft.md`
- `docs/api/error_model.md`

### 4.5 工作流变化

例如：

- Knowledge Assistant 主链路变化
- 状态对象变化
- 错误路径变化
- 新增人工审核节点

必须更新：

- `docs/workflows/knowledge_assistant_flow.md`
- `docs/workflows/workflow_state_objects.md`
- `docs/workflows/workflow_error_paths.md`

### 4.6 关键架构决策变化

例如：

- 决定采用某个中间件
- 决定放弃某个技术路线
- 决定引入新仓 / 新服务

必须新增或更新：

- `docs/decisions/adr_xxx_*.md`

### 4.7 开发设计文档变化

例如：

- 新功能需要跨模块协作方案
- 同一能力存在多实现路径并需要方案对比
- 涉及上线风险、回滚路径、灰度策略的设计说明
- 需要给 AI 提供稳定的实现上下文

必须新增或更新：

- `docs/designs/*.md`
- `context/ai_entry.md`（当入口索引需要调整时）

---

## 5. 哪些变更可以延后更新

以下内容可以延后到阶段性整理时再更新：

- 一般性代码重构
- 小范围函数签名调整
- 不影响外部契约的内部实现变化
- UI 微调
- 普通 bugfix
- 测试代码扩充
- 文案优化

这类变更只要不影响项目边界、接口理解和 AI 入口判断，可以暂不更新知识库仓。

---

## 6. 最小联动更新集

为了控制维护成本，规定一个“最小联动更新集”。

每当发生中等以上变更时，至少检查以下 4 个文件是否需要更新：

### 必查文件

1. `context/project_index.md`
2. `context/current_phase.md`
3. `context/frozen_contracts.md`
4. `docs/engineering/repo_map.md`

这 4 个文件构成知识库仓的最低同步底线。

## 7. 推荐联动流程

### 7.1 日常开发流程

适用于普通功能开发。

#### Step 1：先改主工程仓
在 `orionstack` 中完成：

- 代码实现
- 测试
- 运行验证

#### Step 2：判断是否触发知识库同步
判断问题：

1. 是否改变了项目边界
2. 是否改变了模块职责
3. 是否改变了 API、工作流或开发设计方案
4. 是否会影响 AI 继续开发判断

只要有一项为“是”，就应同步知识库仓。

#### Step 3：更新知识库仓
优先更新：

- `context/` 下入口文件
- 对应模块文档
- ADR（如果属于决策变化）
- `docs/designs/` 下对应设计文档（如果属于方案变化）

#### Step 4：双仓提交
建议：

- 主工程仓提交代码
- 知识库仓提交对应文档
- 在 commit message 中互相引用

例如：

主工程仓 commit:
```md
feat: add document reindex endpoint

ref-kb: sync docs/api + docs/workflows + docs/designs
```

知识库仓 commit:
```md
docs: sync reindex endpoint from orionstack

ref-main: feat add document reindex endpoint
updated: api_contract_draft + workflow_state_objects + designs/reindex_plan
```
