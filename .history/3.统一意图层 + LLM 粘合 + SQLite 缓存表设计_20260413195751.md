统一意图层 + LLM 粘合 + SQLite 缓存表设计
1. 文档目标

本文档用于明确当前阶段中，统一意图层、LLM 粘合层与 SQLite 缓存层的关系、职责边界与最小落地设计，回答以下问题：

为什么当前阶段需要统一意图层
LLM 在统一意图层中承担什么角色
为什么缓存应以 SQLite 为主，而不是简单文件缓存
缓存表应该如何设计
如何判断哪些问题适合持久缓存
是否可以先使用在线 LLM，再切换到本地 LLM
2. 背景与现状

当前系统已经具备基础检索链路，但还没有形成统一意图层。现有 query_tokenizer.py 仍然只输出轻量词法特征，包括 normalized、compact 与 terms，说明当前仍属于 query 的词法处理层，而不是业务意图层。与此同时，retrieval_service.py 仍然直接以原始 question 进入检索链路，没有一个统一前置层先将问题收敛为标准化业务意图。

这意味着，当前系统仍然缺少以下能力：

相同业务意图的不同问法归一
LLM 输出收敛为稳定中间结构
相同意图跳过重复解析与重复检索
后续多领域、跨系统、混合问题的统一前置处理能力

因此，当前阶段需要建立统一意图层，并配套引入 SQLite 持久缓存，使高重复问题与高重复意图能够沉淀为可复用的工程资产。

3. 总体定位

本工程的目标不是构建一个脱离 LLM 仍需完整运行的纯规则系统，而是为传统业务系统添加 LLM 能力，并将文档、制度、FAQ、流程说明与业务系统入口粘合在一起，达到以下目标：

省时
省步骤
降低理解成本
降低重复问答成本
为后续多系统接入保留统一入口

因此，本阶段不必强调“离开 LLM 可完整可用”，但必须强调：

LLM 是正式能力组件之一
LLM 输出必须收敛到统一结构
LLM 失败时系统行为仍需可预测
重复问题不应每次都重新走完整链路
4. 统一意图层的职责

统一意图层位于检索之前，负责把原始自然语言问题转换为可消费的稳定业务意图对象。

统一意图层负责：

query 归一
动作识别
业务域识别
业务对象识别
子类型识别
检索表达生成
意图签名生成
为缓存提供稳定 key

统一意图层不负责：

最终答案组织
FAQ 文案维护
文档内容改写
系统执行
跨系统编排
多轮状态管理

统一意图层输出应为统一结构，而不是自由文本。建议至少包含以下字段：

raw_query
normalized_query
domains
actions
entities
subtypes
retrieval_terms
intent_signature
intent_version
5. LLM 在体系中的角色
5.1 LLM 作为粘合判断层

LLM 在本体系中的定位不是直接替代规则，也不是直接代替最终答案生成链路，而是作为统一意图层中的单意图层级判断器。

更合理的角色分工如下：

规则 / 词典：负责显性词命中、基础约束、稳定别名归一
LLM：负责单意图层级判断、自然表达归并、模糊 query 收敛
统一意图契约：负责把不同实现方式的输出收敛到固定结构

也就是说，LLM 是统一意图层中的粘合组件，而不是自由漂移的独立回答器。

5.2 模型使用模式

建议统一意图层支持三种模式：

rule_only
只使用规则与词典
rule_plus_online_llm
规则保底，在线 LLM 做单意图判断
rule_plus_local_llm
规则保底，本地 LLM 做单意图判断

三种模式都必须输出同一个统一意图对象，下游不应直接依赖某个具体模型的自由文本结果。

6. 是否可以先用在线 LLM，再切换到本地 LLM

可以，而且这种路线是合理的。

但这里需要区分两件事：

6.1 可以做的事

当前工程中，完全可以采用以下路径：

早期阶段用在线 LLM 做单意图判断、query 归一、领域识别
在业务词典、意图契约、缓存机制稳定之后，再切换到本地 LLM
或者保留在线 / 本地双模式，通过配置切换

这种做法的价值在于：

早期准确率更高，便于快速验证统一意图层结构
后期可根据成本、时延、数据要求切到本地模型
统一意图契约不变，切模型不会带来下游接口震荡
6.2 不建议误写成“预训练”

如果这里说的“预训练”指的是：

先用在线 LLM 做运行时判断
后期切换到本地 LLM 继续承担同一职责

这是可以的。

但如果这里的“预训练”指的是：

训练模型权重
对模型做真正的预训练 / 微调工程

那就不是当前阶段的主线。
当前阶段更适合做的是：

在线模型先承担运行时判断
同时积累意图样本、缓存命中数据、错误样本
后续再评估是否需要做 prompt 固化、轻量蒸馏、SFT 或更深一步模型适配

因此，本阶段路线建议表述为：

先使用在线 LLM 作为统一意图层判断器，再逐步切换或扩展到本地 LLM；不是当前阶段就把模型训练本身作为主任务。

7. 统一意图层与检索链路的关系

统一意图层应位于检索前，形成如下主链路：

原始问题
→ 统一意图层（规则 + LLM 单意图判断）
→ 产出标准化检索表达
→ 检索
→ 命中证据
→ 回答组织
→ 返回引用

当前代码结构表明，这个前置层还没有建立，因为 query_tokenizer.py 目前仍只是词法层，retrieval_service.py 也仍然直接消费原始 question。

统一意图层建成后，系统主要消费的是意图层产出的标准化表达，而不只是原始问句文本。

8. 为什么需要 SQLite 缓存

统一意图层建立后，相同问法会收敛到相同或高度相似的意图签名，此时缓存的最佳粒度就不再是“原始句子”，而是“意图签名”。

相比文件缓存，SQLite 更适合当前阶段，原因如下：

更适合按 intent_signature 查询
更适合记录命中次数与时间窗口
更适合记录文档版本与缓存失效条件
更适合做分层缓存
更适合后续做高重复问题统计
对当前单机 / 轻量服务场景足够合适

因此，本阶段建议：

调试期可临时使用文件缓存
正式落地以 SQLite 为主
9. 缓存分层设计

缓存不应只设计成一种，而应分成三层。

9.1 意图解析缓存

用于缓存统一意图层输出结果。

缓存内容包括：

原始 query
归一 query
domains
actions
entities
subtypes
retrieval_terms
intent_signature
intent_version
使用的 LLM 模式
命中次数与最近命中时间

这一层最值得优先做，因为：

命中率高
体积小
不依赖文档内容版本
可显著减少重复 LLM 判断
9.2 证据缓存

用于缓存某个意图对应的稳定命中证据。

缓存内容包括：

intent_signature
document_id
chunk_id
snippet
document_version
检索来源
命中分数摘要
命中次数与最近命中时间

这一层适合缓存“某个意图通常命中哪些证据”。

9.3 答案缓存

用于缓存稳定 FAQ 的最终答案。

缓存内容包括：

intent_signature
answer_text
citations
doc_version_snapshot
cache_level
created_at
last_hit_at
expires_at

答案缓存只适用于：

单领域
单意图
内容稳定
用户无关
状态无关
依赖文档而非实时系统数据
10. 高重复问题判定策略

高重复问题不应只靠人工感觉判断，应形成可观测规则。

10.1 建议判定维度

一个问题可以被视为高重复问题，通常满足以下条件中的多数：

相同 intent_signature 在时间窗口内重复出现
多次命中的证据集合高度稳定
结果不依赖用户私有状态
结果不依赖实时系统状态
命中文档版本长期稳定
问题属于制度 / 流程 / FAQ 型问题
10.2 建议分级

建议分成三类：

A 类：高重复稳定 FAQ
可持久缓存意图、证据、答案
B 类：高重复但答案需谨慎
可持久缓存意图与证据，不直接长期缓存答案
C 类：状态型或用户相关问题
仅缓存意图解析，不缓存最终答案
11. SQLite 缓存表设计

本阶段建议至少设计四张表。

11.1 intent_cache

用于缓存统一意图层结果。

表职责
按 intent_signature 持久化意图解析结果
记录命中频率

用于缓存意图对应的稳定证据。

表职责
记录某个意图通常命中哪些文档块

12. 建议 SQL 结构示意
CREATE TABLE intent_cache (
    intent_signature TEXT PRIMARY KEY,
    raw_query_hash TEXT NOT NULL,
    raw_query_sample TEXT NOT NULL,
    normalized_query TEXT NOT NULL,
    domains_json TEXT NOT NULL,
    actions_json TEXT NOT NULL,
    entities_json TEXT NOT NULL,
    subtypes_json TEXT NOT NULL,
    retrieval_terms_json TEXT NOT NULL,
    intent_version TEXT NOT NULL,
    llm_mode TEXT NOT NULL,
    model_name TEXT,
    created_at TEXT NOT NULL,
    last_hit_at TEXT NOT NULL,
    hit_count INTEGER NOT NULL DEFAULT 1,

    id INTEGER PRIMARY KEY AUTOINCREMENT,

13. 缓存失效策略

缓存必须可失效，不能只写不清理。

13.1 文档版本失效

当意图关联的 FAQ 文档版本变更时：

证据缓存需要失效或降级
答案缓存需要失效或重建
13.2 时间窗口失效
稳定 FAQ 的答案缓存可设置长 TTL
半稳定 FAQ 的答案缓存可设置短 TTL
状态型问题不缓存最终答案
13.3 配置版本失效

如果以下任一版本变化较大：

意图层版本
词典版本
模型模式
模型名称
prompt 版本

则相关缓存需具备重建能力。

13.4 命中证据漂移失效

如果同一意图最近多次命中的证据集合明显变化，说明缓存稳定性下降，应降级或重建。

14. 在线 LLM 到本地 LLM 的切换策略

本设计天然支持在线 LLM 与本地 LLM 切换。

14.1 推荐切换方式

建议保持以下稳定层不变：

统一意图契约
SQLite 表结构
intent_signature 生成规则
retrieval_terms 输出接口

只替换以下可配置项：

llm_mode
model_name
prompt 配置
超时与重试策略
14.2 推荐阶段路线
阶段一：在线 LLM 优先

目标：

快速验证统一意图层结构
快速观察高重复问题分布
快速积累意图样本与错误样本
阶段二：在线 / 本地双模式

目标：

在线模型作为高精度模式
本地模型作为常规模式
通过配置切换
阶段三：本地 LLM 主模式

目标：

在意图契约、词典与缓存机制稳定后，将主模式切到本地 LLM
在线模型退为补充或调试模式

因此，这种设计完全支持“先在线 LLM，后本地 LLM”的路线。

15. 当前阶段落地建议

本阶段建议按以下优先级推进：

建立统一意图契约
引入 LLM 作为单意图判断器
先落地 intent_cache
再落地 evidence_cache
只对高重复稳定 FAQ 开启 answer_cache
使用 SQLite 而不是正式文件缓存
第一阶段先覆盖假勤域等高频 FAQ 域

本阶段不做：

多领域完整注册中心
多意图完整拆解
跨系统自动执行
分布式缓存体系
模型训练工程
16. 一句话总结

统一意图层的核心价值，不只是统一 query，而是把 LLM 的判断结果收敛为可缓存、可复用、可治理的中间结构。

在缓存层面，应优先缓存意图解析结果与证据命中结果，并以 SQLite 作为正式持久缓存介质；对于高重复、稳定、用户无关、状态无关的 FAQ，再选择性缓存最终答案。

这种设计完全支持先使用在线 LLM 做统一意图判断，再通过配置平滑切换到本地 LLM，而无需推翻统一意图契约与缓存表结构。
