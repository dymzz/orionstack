## 1. 文档目标

本文档用于给出 OrionStack 的**短版架构总览**，回答以下问题：

1. OrionStack 当前到底是什么
2. 当前阶段只做什么，不做什么
3. 系统按什么层次组织
4. 为什么首期聚焦知识助手 / 文档问答
5. 在企业旧系统环境下，OrionStack 应如何接入而不是失控扩张

本文档不是长篇设计说明，不展开历史演进与详细论证。  
它的目标是为工程开发、代码阅读、文档对齐与 AI 辅助开发提供统一入口。

---

## 2. 一句话定位

**OrionStack 是一套面向企业 AI 过渡期的模块化应用底座，用于以可控、可扩展、可治理的方式，将 LLM 能力稳定接入企业现有系统，并优先支撑知识助手 / 文档问答等高价值场景。**

在当前阶段，OrionStack 不应被理解为：

- 底层模型平台
- 通用 Agent 平台
- 大而全企业 AI 后台
- 旧 ERP / OA / 权限系统替代层

它当前更准确的定位是：

> **企业 AI 交互层、知识增强层、建议层与工作流编排层。**

---

## 3. 当前阶段与首期目标

### 3.1 当前阶段

当前主阶段为：

**Phase 1 - 知识助手 MVP**

当前首要目标是打通以下主链路：

- 文档上传
- 索引构建
- 检索问答
- 引用返回
- 会话、日志与反馈基础链路

当前首个场景为：

**企业知识助手 / 文档问答**

### 3.2 当前阶段只做什么

当前阶段只做：

- 知识助手 / 文档问答
- 文档上传与索引
- 检索问答与引用返回
- 会话、日志、反馈基础链路
- 面向旧系统环境的建议型接入准备

### 3.3 当前阶段明确不做什么

当前阶段明确不做：

- 客服 / 工单场景
- 运维 / 安全辅助场景
- 多 Agent 协同
- 大而全平台后台
- 自动审批、自动流转、自动写入旧系统
- 以替代 ERP / OA / 权限系统为目标的重构工程

当前阶段的核心目标不是“支持很多场景”，而是：

> **把知识问答这一条主链路做深、做稳、做可追溯。**

## 4. 总体架构思路

OrionStack 当前采取的是**模块化分层架构**。

其核心判断是：

- 企业 AI 应用存在大量共性能力
- 这些共性能力适合按层拆分，而不是一开始做大而全平台
- 首期应先围绕单一高价值场景完成 MVP
- 架构扩展必须建立在已跑通的主链路之上，而不是抽象优先

因此，OrionStack 当前并不追求“一步到位的平台化”，而是通过以下方式推进：

1. 先确定首个高价值场景：知识助手 / 文档问答
2. 先跑通完整闭环：上传 → 索引 → 检索 → 问答 → 引用 → 反馈
3. 再把其中可复用能力沉淀为分层模块
4. 后续再评估是否扩展到其他相邻场景

## 5. 当前阶段技术抽象原则

在当前阶段，OrionStack 采用“主链路优先、薄抽象优先、平台化后置”的技术策略。

这意味着：

- 当前优先保证知识助手 / 文档问答主链路可运行、可追溯、可稳定演进
- 当前不为了未来平台化而提前引入额外框架包装层
- 当前不让 LangChain / LangGraph 接管 API、数据访问、旧系统适配与治理真源层

在当前阶段，LangChain / LangGraph 可以保留为后续可选能力，  
但它们不是当前主链路的必需前提。

当前阶段更推荐的实现方式是：

- API 层保持薄
- 服务与知识主链路保持直连
- 数据真源层保持纯净
- 工作流层保持轻量骨架
- 只在明确出现重复问题或第二场景时，再评估是否引入更高层抽象

一句话概括：

> 当前阶段优先做清晰可读的直连实现，而不是引入会放大复杂度的框架接管。

## 6. 系统分层总览

当前可将 OrionStack 粗分为五层。

### 6.1 前端工作台层

负责：

- 用户交互
- 会话呈现
- 文档管理
- 引用展示
- 结果反馈

当前前端形态以知识助手工作台为主，不追求复杂后台系统。

### 6.2 API 接入层

负责：

- 接收前端请求
- 参数校验
- 请求路由
- 统一返回结构
- 基础上下文透传

这一层不承载复杂业务判断，主要作为系统对外接口面。

### 6.3 工作流编排层

负责：

- 组织问答主链路
- 管理知识助手状态
- 承接后续工作流扩展
- 为不同节点提供清晰执行边界

当前阶段可使用 LangGraph 作为工作流骨架，但工作流本身仍应保持轻量，不提前扩展为复杂多 Agent 系统。

### 6.4 知识能力层

负责：

- 文档接入
- 文本解析
- 索引构建
- 检索召回
- 重排与引用组织
- 问答上下文构建

这一层是当前 MVP 的核心价值承载层。  
LlamaIndex 等能力应主要用于知识层，而不是反客为主成为整个系统骨架。

### 6.5 治理与支撑层

负责：

- 权限边界
- 日志与审计
- 错误处理
- 会话记录
- 反馈闭环
- 运行时支撑能力

这一层在当前阶段只做必要最小集，不做重型平台治理系统。

---

## 7. 当前主链路

当前阶段的主链路可以概括为：

**文档上传 → 文档解析 → 索引构建 → 检索召回 → 问答生成 → 引用返回 → 历史记录与反馈**

其核心目标不是“让模型随便回答”，而是：

- 尽量基于可追溯知识回答
- 尽量返回清晰引用
- 尽量保留会话与反馈基础链路
- 在回答能力不足时能够诚实降级

在当前阶段，问答主链路是系统最优先保障对象。  
其他能力如复杂 Tool 编排、跨系统执行、自动审批等，不进入首期主链路。

## 8. 旧系统接入边界

### 8.1 为什么要强调旧系统边界

企业真实环境中通常已经存在：

- ERP
- OA
- 权限系统
- 组织系统
- 历史工具封装层
- 审批与执行链路

因此，OrionStack 的设计前提不能是“替换旧系统”，而必须是：

> **在旧系统持续存在的前提下，以非侵入方式接入 AI 能力。**

### 8.2 当前阶段的旧系统定位

在当前阶段，旧 ERP / OA / 权限系统仍然是：

- 事实来源
- 权限来源
- 审批来源
- 最终执行系统

OrionStack 不承担：

- 替代旧系统
- 重写旧权限体系
- 推翻旧 Tool 封装层
- 接管旧审批流与自动执行链路

### 8.3 当前阶段的接入原则

首期旧系统接入遵循以下原则：

1. **非侵入优先**  
   如无必要，不修改旧系统本体。

2. **既有 Tool 封装层可保留**  
   首期允许复用旧 wrapper / tool 层，不要求立即停用。

3. **默认只做只读与建议型接入**  
   首期接入以读型问题和建议型辅助为主。

4. **执行型能力后置**  
   涉及写入、审批、变更、自动执行的能力首期不纳入主链路。

5. **问答能力优先放行**  
   对于制度解释、流程说明、知识检索、文档问答等问题，可以直接回答并返回引用。

### 8.4 旧系统接入分层建议

当前阶段推荐采用以下接入方式：

- 旧系统层：ERP / OA / 权限 / 审批等既有系统
- 旧 Tool 封装层：既有接口封装、服务代理、脚本工具
- OrionStack 适配层：统一上下文、参数、权限结果与错误结构
- Tool Gateway / 工作流层：负责调用治理与编排
- 问答与建议输出层：向用户输出回答、引用、建议、入口与参数草稿

这意味着首期最合理的定位不是“自动执行很多动作”，而是：

> **先把问答、解释、建议、引用做强。**

## 9. 首期最适合优先落地的能力

在企业旧系统广泛存在的前提下，当前阶段最适合优先落地的是以下三类能力：

### 9.1 文档问答型能力

例如：

- 制度问答
- FAQ 问答
- 流程文档解释
- 操作手册问答
- 企业知识检索与引用返回

这是当前 MVP 的核心落点。

### 9.2 流程建议型能力

例如：

- 该走哪个 OA 流程
- 应准备哪些字段
- 下一步通常由谁处理
- 该去哪个旧系统模块操作

这类能力首期只输出建议，不直接执行。

### 9.3 跳转辅助型能力

例如：

- 返回旧系统入口
- 返回相关表单入口
- 返回相关制度文档
- 返回相关流程说明与注意事项

这类能力风险低、价值直观，适合作为首期辅助能力。

---

## 10. 首期真正需要做深的优势

当前阶段不应以“覆盖场景很多”作为主要成功标准，  
而应以“少数关键能力是否做深”作为判断标准。

首期最值得持续做深的能力包括：

### 10.1 可追溯引用

系统给出的回答，不只是能说，还必须能指出：

- 依据来自哪份文档
- 依据来自哪段内容
- 引用是否可返回给前端展示

### 10.2 权限感知检索

系统只能基于用户有权访问的内容进行检索与回答。  
权限边界应由系统层与检索层保证，而不依赖模型自行判断可见范围。

### 10.3 建议型流程辅助

对于 ERP / OA / 旧 Tool 相关问题，首期优先输出：

- 建议
- 步骤
- 入口
- 参数草稿
- 注意事项

而不是自动执行。

### 10.4 反馈闭环

系统应记录：

- 问答结果
- 引用结果
- 用户反馈

为后续的检索优化、知识清洗、提示词优化与能力扩展提供依据。

---

## 11. 当前工程落点

从工程实现角度看，当前阶段最重要的是围绕知识助手主链路完成最小闭环，而不是继续横向扩张。

因此，当前工程重点应始终围绕以下模块收敛：

- API 路由与数据契约
- 文档上传与解析
- 索引与检索
- 问答与引用返回
- 会话、反馈与日志
- 最小必要的权限与审计能力

后续扩展必须建立在这条主链路已经稳定的基础上。

---

## 12. 当前阶段一句话总结

**OrionStack 当前阶段是一个面向企业旧系统环境的知识问答与建议型 AI 应用底座 MVP。**

它当前不替代旧系统，  
而是在旧系统之上，以可控、可追溯、可逐步扩展的方式接入 LLM 能力。

其首期最重要的优势不在于“大而全”，而在于：

- 可追溯引用
- 权限感知检索
- 建议型流程辅助
- 反馈闭环
