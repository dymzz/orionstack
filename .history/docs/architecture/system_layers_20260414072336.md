## 1. 文档目标

本文档用于定义 OrionStack 当前阶段的**系统分层结构**，回答以下问题：

1. OrionStack 当前阶段按哪些层组织
2. 每一层的职责边界是什么
3. 每一层的输入输出如何理解
4. 为什么要按这些层拆，而不是把能力混在一起
5. 在首期知识助手 / 文档问答 MVP 中，各层的优先级与演进方向是什么

本文档不是长篇设计论证，也不是接口明细文档。  
它的目标是给开发、重构、代码阅读、AI 辅助开发提供一个统一的分层视图。

---

## 2. 分层设计原则

OrionStack 当前阶段采用分层结构，遵循以下原则：

### 2.1 单层职责尽量单一

每一层优先解决一种核心问题，避免：

- API 层承载过多业务逻辑
- 工作流层直接处理底层存储细节
- 知识层直接暴露复杂业务判断
- 模型层反客为主，吞掉系统边界

### 2.2 分层为当前 MVP 服务，而不是为未来过度设计

当前分层的目标不是“一次性设计完未来平台”，  
而是为了让首期知识助手主链路具备：

- 更清楚的代码边界
- 更低的耦合风险
- 更好的后续替换能力
- 更可控的扩展路径

### 2.3 旧系统接入必须非侵入

旧 ERP、OA、权限系统与既有 Tool 封装层，当前阶段不应被 OrionStack 直接替代。  
接入时应通过适配层、Gateway 或只读 / 建议型方式完成，避免把旧系统耦合进问答主链路。

### 2.4 当前阶段优先保障问答主链路

首期所有分层设计，最终都应服务于以下主链路：

**文档上传 → 文档解析 → 索引构建 → 检索召回 → 问答生成 → 引用返回 → 反馈闭环**

## 3. 总体分层视图

在当前阶段，OrionStack 可分为以下六层：

1. 前端工作台层
2. API 接入层
3. 应用服务层
4. 工作流编排层
5. 知识能力层
6. 治理与支撑层

其中：

- 前端工作台层负责用户交互
- API 接入层负责对外暴露接口
- 应用服务层负责承接单次业务动作
- 工作流编排层负责组织多步骤链路
- 知识能力层负责知识接入、索引、检索与引用
- 治理与支撑层负责权限、审计、日志、反馈等横切能力

这六层不是为了“层数好看”，  
而是为了把当前最容易混在一起的职责拆开。

## 4. 当前阶段框架接入边界

在当前阶段，OrionStack 采用“分层清晰、主链路直连、框架后置”的技术策略。  
这意味着 LangChain / LangGraph 不应在所有层中自由扩散，而必须受层边界约束。

### 4.1 前端工作台层

前端工作台层只负责：

- 用户交互
- 文档管理
- 问答展示
- 引用展示
- 与后端 API 通信

因此，前端层不应引入 LangChain 风格抽象。  
前端不负责 chain、tool orchestration、prompt pipeline 或模型执行语义。

### 4.2 API 接入层

API 层只负责：

- 路由暴露
- 参数校验
- 响应结构统一
- 请求分发

因此，API 层不应直接承载 LangChain chain / runnable / prompt orchestration。  
API 层一旦被框架执行路径接管，会破坏接口层与业务层之间的清晰边界。

### 4.3 模型层与仓储层

`models/` 与 `repositories/` 当前阶段必须保持纯净：

- 模型层只负责实体与 ORM 定义
- 仓储层只负责数据访问与存储细节封装

因此，这两层不应引入 LangChain 风格对象，不应与 chain state、message wrapper 或框架执行语义耦合。

### 4.4 基础支撑层与迁移层

`core/`、`config/`、`migrations/` 属于基础设施层。  
这一层必须尽量稳定、通用、低耦合，因此不应引入 LangChain 依赖来驱动其职责。

### 4.5 旧系统接入层

`integrations/` 的职责是：

- 旧 ERP / OA / 权限系统适配
- 外部系统接入
- 旧 Tool 封装层复用

当前阶段该层强调非侵入、建议优先、执行后置。  
因此，这一层不应由 LangChain 接管，不应演变为框架驱动的执行层。

### 4.6 治理与真源层

审计、反馈、历史记录、trace 等能力属于治理真源层。  
该层必须保持可追踪、可验证、可独立演进，因此不应依赖 LangChain 风格对象作为真源数据结构。

### 4.7 当前阶段允许保留的框架位置

当前阶段允许保留的仅是：

- LangGraph 作为轻量工作流骨架的未来扩展位
- LangChain 作为后续可能统一模型调用、工具注册或结构化输出的候选方案

但前提是：

- 当前主链路已经稳定
- 出现明确的第二场景
- 现有直连实现开始重复
- 引入框架能够降低复杂度，而不是增加包装层

### 4.8 当前阶段结论

当前阶段的系统分层，不以框架优先为原则，而以职责边界优先为原则。  
因此：

> LangChain / LangGraph 当前不应进入接口契约层、数据真源层、旧系统适配层与主链路执行层。  
> 它们只能作为后续可选能力保留，而不是当前核心实现前提。

## 5. 前端工作台层

### 5.1 目标

前端工作台层负责承载用户与系统的直接交互，  
让知识助手、文档管理、引用展示与反馈动作具备统一交互入口。

### 5.2 当前职责

当前阶段前端工作台层主要负责：

- 知识问答交互
- 会话展示
- 文档上传与管理
- 引用展示
- 基础反馈入口
- 与后端 API 的请求交互

### 5.3 当前阶段不承担的职责

当前阶段前端工作台层不承担：

- 复杂业务编排逻辑
- 直接操作底层知识索引
- 权限判定主逻辑
- 复杂多角色后台系统能力
- 多场景统一门户

### 5.4 输入与输出

**输入：**
- 用户问题
- 用户上传的文档
- 会话操作
- 反馈操作

**输出：**
- API 请求
- 问答结果展示
- 引用结果展示
- 反馈动作提交

### 5.5 当前阶段落点

当前前端应以“知识助手工作台”形态为主，  
不提前扩展为复杂运营后台或全场景企业门户。

---

## 6. API 接入层

### 6.1 目标

API 接入层负责把系统能力以清晰、稳定、可验证的方式暴露出来，  
并作为前端、外部调用者与系统内部能力之间的边界层。

### 6.2 当前职责

API 接入层主要负责：

- 路由注册
- 请求参数校验
- 响应结构统一
- 会话与追踪上下文透传
- 将请求分发给应用服务层或工作流层

### 6.3 当前阶段不承担的职责

API 接入层不应直接承担：

- 复杂业务规则
- 多步骤工作流编排
- 底层文档检索细节
- 直接操作旧系统接入逻辑
- 模型提示词构造与答案生成细节

### 6.4 输入与输出

**输入：**
- HTTP 请求
- 请求头、用户上下文、trace 信息
- 前端或外部系统提交的 payload

**输出：**
- 标准化响应
- SSE 流式响应
- 标准化错误结果
- 追踪 ID / 响应元信息

### 6.5 当前阶段落点

当前 API 层应保持薄，  
主要作为系统入口，而不是业务堆积区。

---

## 7. 应用服务层

### 7.1 目标

应用服务层用于承接**单次业务动作**，  
将 API 层的请求转化为系统可执行的应用级操作。

它是“接口层”和“内部能力层”之间的中间收敛层。

### 7.2 当前职责

应用服务层主要负责：

- 承接单次问答请求
- 承接单次文档上传请求
- 承接会话与历史记录动作
- 承接反馈提交动作
- 协调知识能力层与仓储层完成一次完整动作

### 7.3 当前阶段不承担的职责

应用服务层不应承担：

- 长链路工作流状态机
- 复杂跨场景编排
- 与旧系统的直接深度耦合
- 过重的横切治理逻辑

### 7.4 输入与输出

**输入：**
- API 层传入的结构化请求对象
- 用户上下文
- 请求级 trace 信息

**输出：**
- 单次业务动作结果
- 问答响应
- 文档处理结果
- 历史记录与反馈结果

### 7.5 当前阶段落点

当前阶段应用服务层应优先保持“薄协调、少逻辑”，  
只承接首期知识问答与文档主链路所需动作。

---

## 8. 工作流编排层

### 8.1 目标

工作流编排层负责组织**多步骤链路**，  
把多个能力节点串成一条可理解、可追踪、可扩展的执行路径。

### 8.2 当前职责

当前阶段工作流层主要负责：

- 表达知识助手主链路状态
- 管理问答相关步骤的执行顺序
- 为后续节点扩展预留位置
- 承接 LangGraph 等工作流骨架能力

### 8.3 当前阶段不承担的职责

当前阶段工作流层不应承担：

- 复杂多 Agent 协同
- 大规模通用调度平台职责
- 直接承载知识检索底层实现
- 直接调用旧系统细节接口
- 复杂审批与执行链路控制

### 8.4 输入与输出

**输入：**
- 应用服务层发起的工作流请求
- 当前会话状态
- 必要上下文与用户输入

**输出：**
- 有顺序的节点执行结果
- 问答主链路状态
- 节点中间结果
- 可供应用服务层消费的最终输出

### 8.5 当前阶段落点

当前阶段工作流层可以存在，但应保持轻量。  
重点是清晰表达主链路，而不是提前做成复杂流程平台。

---

## 9. 知识能力层

### 9.1 目标

知识能力层是 OrionStack 当前 MVP 的核心层。  
它负责把原始文档和知识内容转化为系统可检索、可引用、可问答的上下文能力。

### 9.2 子层划分

当前知识能力层可进一步拆为四个子方向：

1. 接入与解析
2. 索引构建
3. 检索与重排
4. 引用与上下文组织

### 9.3 接入与解析子层

负责：

- 接收上传文档
- 识别文档类型
- 提取文本内容
- 为后续索引提供标准化输入

当前阶段优先服务：

- 文档问答
- 企业知识文档接入
- 基础可解析格式

### 9.4 索引构建子层

负责：

- 文本切块
- 元数据组织
- embedding 构建
- 索引写入
- 索引任务调度

该层的核心目标不是“把所有技术都堆进来”，  
而是先稳定打通文档到索引的主链路。

### 9.5 检索与重排子层

负责：

- 基于问题召回候选片段
- 在候选结果中做排序优化
- 为问答层输出更相关的上下文
- 为引用层提供候选来源

当前阶段应优先保证：

- 能检索到
- 能返回可追溯来源
- 权限边界可控
- 排序逐步可优化

### 9.6 引用与上下文组织子层

负责：

- 组织回答所需上下文
- 绑定引用来源
- 向上层输出 citation 结果
- 支撑前端进行引用展示

这是当前阶段最值得做深的部分之一，因为它直接决定：

- 回答是否可信
- 结果是否可追溯
- 企业用户是否愿意信任系统输出

### 9.7 当前阶段不承担的职责

知识能力层当前不应承担：

- 平台级知识中台职责
- 通用内容治理平台职责
- 复杂跨系统执行编排
- 直接决定权限可见性最终策略
- 全场景企业知识统一底座

### 9.8 当前阶段落点

当前阶段知识能力层只围绕“知识助手 / 文档问答 MVP”建设。  
它是首期最核心的能力层，也是首期最重要的差异化来源。

---

## 10. 治理与支撑层

### 10.1 目标

治理与支撑层负责承接所有**横切能力**，  
避免这些能力散落到各业务层中，造成系统边界混乱。

### 10.2 当前职责

当前阶段治理与支撑层主要负责：

- 权限边界承接
- 请求上下文管理
- 审计与日志
- 历史记录
- 用户反馈
- 错误处理与基本回退
- 运行时数据库与存储支撑

### 10.3 权限边界原则

在当前阶段，权限相关能力应遵循以下原则：

- 用户权限来源于旧权限系统或既有认证体系
- 可见性判断优先在系统层与检索层收敛
- 不将“哪些内容能看”交给模型自行判断

也就是说：

> 模型只基于允许看到的上下文回答，  
> 而不是自己决定哪些文档可以暴露给用户。

### 10.4 审计与反馈原则

当前阶段治理层应至少支持：

- 请求 trace
- 问答历史记录
- 基础审计信息
- 用户反馈收集

其目标不是一开始就做重型治理平台，  
而是先形成最小可追踪闭环。

### 10.5 当前阶段落点

治理与支撑层在首期只做必要最小集。  
它的职责是为主链路兜底，而不是喧宾夺主。

---

## 11. 旧系统接入层次关系

在企业真实环境下，OrionStack 与旧系统的关系应理解为：

1. 旧系统层仍然是事实来源与最终执行系统
2. 旧 Tool 封装层允许继续保留
3. OrionStack 通过适配层与 Gateway 进行接入
4. 首期优先只做只读与建议型能力
5. 自动执行型能力后置，不进入 MVP 主链路

这意味着，在系统分层上：

- 旧 ERP / OA / 权限系统不属于 OrionStack 内部核心层
- 旧系统只通过接入适配与 Tool 能力被上层消费
- 首期问答层不直接承担深写入逻辑

---

## 12. 当前阶段层间关系总结

当前阶段，各层关系可以概括为：

- 前端工作台层：负责人与系统交互
- API 接入层：负责接口暴露与参数边界
- 应用服务层：负责承接单次业务动作
- 工作流编排层：负责组织多步骤链路
- 知识能力层：负责知识接入、索引、检索、引用
- 治理与支撑层：负责横切能力与最小兜底

其中，当前阶段最关键的两层是：

1. **知识能力层**
2. **治理与支撑层中的引用、权限、反馈部分**

因为首期真正的差异化并不在“做很多场景”，  
而在于把以下能力做深：

- 可追溯引用
- 权限感知检索
- 建议型流程辅助
- 反馈闭环

---

## 13. 当前阶段一句话总结

在当前阶段，OrionStack 的系统分层设计服务于一个明确目标：

**以最小必要分层支撑知识助手 / 文档问答 MVP，  
在不替代旧系统的前提下，把问答、引用、权限感知与反馈闭环做深。**

后续所有扩展，都应建立在当前分层边界已经清晰、主链路已经稳定的前提之上。
