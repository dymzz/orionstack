## Project stage

This repository is currently in **Phase 1: knowledge assistant MVP**.

The priority is:

- main path first
- thin abstraction first
- minimal effective implementation first

Do not expand scope unless explicitly required.

---

## Core engineering rule

For the current stage, documentation boundaries must become **default runtime behavior**.

Do not treat architecture docs as passive description.
Implement them as executable defaults.

If the documented boundary says a simple document-QA problem should take the light path, then the code default must also take the light path.

---

## Default behavior for simple QA

For simple FAQ / single-topic / direct procedure questions, the default execution path must be:

`user question`
-> `optional minimal query rewrite for retrieval terms only`
-> `embedding retrieval`
-> `top 1-3 chunks`
-> `direct answer from those chunks`

For this class of questions, default behavior must be:

- rerank OFF
- model-based evidence extraction OFF
- no candidate-topic enumeration
- no heavy post-retrieval LLM chain
- no extra orchestration layer

---

## What counts as a simple question

Treat questions like these as simple-path questions:

- 如何请假
- 怎么请假
- 病假怎么申请
- 事假怎么申请
- 年假余额在哪里看
- 会议室如何预订
- 报销多久到账

Common traits:

- single topic
- answer likely exists in one FAQ entry or one short section
- no multi-document synthesis required
- no complex reasoning chain required

## Scope discipline

When solving a bug or quality issue:

1. prefer the smallest mergeable fix
2. fix the current path before discussing redesign
3. do not introduce new abstraction layers unless absolutely required
4. do not turn simple problems into framework problems

Forbidden by default:

- architecture redesign
- LangChain expansion
- new orchestration layer
- generic agent framework
- database schema changes
- frontend redesign
- “future extensibility” work not required by the task
- unrelated cleanup

---

## Retrieval discipline

Rules are only allowed to preserve or enforce execution boundaries.
Do not build a heavy rule system that replaces embedding or LLM.

Use this division of responsibility:

- retrieval gets relevant chunks
- LLM rewrites query minimally when needed
- LLM explains retrieved evidence clearly
- runtime defaults must stay light for simple questions

Do not use extra LLM steps unless they are clearly necessary for the current task.

---

## Required working style

For every coding task, respond in this order:

1. current goal
2. source files used
3. minimal change locations
4. expected effect
5. verification steps

Keep changes localized.
Do not silently expand scope.

---

## Output requirements

When implementing a fix, always report:

1. root cause summary
2. exact files changed
3. what default runtime behavior changed
4. how to verify the fix
5. remaining risks

Do not provide multiple redesign options unless explicitly requested.

---

## Success criteria for QA fixes

A QA fix is only considered complete if:

- the answer becomes narrower and more relevant
- latency is reduced for simple questions
- token usage is reduced for simple questions
- unrelated topic expansion disappears
- the change is minimal and localized
- documented project boundaries are reflected in runtime defaults

---

## Current repository-specific directive

For simple FAQ / procedure-style document QA, do not let the default runtime path become:

`retrieval -> heavy rerank -> model evidence filtering -> candidate topic expansion -> answer`

Prefer:

`minimal query rewrite -> embedding retrieval -> top chunks -> direct answer`

This repository should solve simple document-QA problems with the shortest correct path.
