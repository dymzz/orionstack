# OrionStack 文档接入与清洗边界说明 v1

> 状态：边界冻结文档（新增）  
> 适用范围：`1_system_design.md` + `2_system_design.md`  
> 文档位置建议：`docs/architecture/document_ingestion_boundary.md`  
> 关联文档：`1_system_design.md`、`2_system_design.md`

---

## 1. 文档目标

本文档用于明确 OrionStack 在“原始文档进入问答系统之前”所需的最小接入与清洗边界。

本文档只回答以下问题：

1. 哪些输入可以直接进入当前 FAQ / 文档问答主链路
2. 哪些输入必须先经过文档清洗 / ingestion adapter
3. 文档清洗层负责什么、不负责什么
4. `1_system_design.md` 与 `2_system_design.md` 应如何衔接该边界

本文档不承担以下职责：

- 不把 OrionStack 重写为通用文档平台
- 不把当前主系统改写为重型知识中台
- 不预埋大而全的多源治理与复杂编排平台
- 不冻结完整 `Knowledge Unit` 字段契约
- 不承担字段定义表职责
- 不讨论与当前主链路无关的远期平台化蓝图

---

## 2. 文档定位

### 2.1 一句话定位

OrionStack 的主系统仍然是 **FAQ / 业务知识问答系统**；  
`document_ingestion_boundary.md` 只负责定义：

**原始文档如何在进入检索问答主链路前，被判断、接入、清洗，并转换为下游可消费的知识输入。**

### 2.2 与现有系统设计文档的关系

- `1_system_design.md`：继续定义当前问答主链路，不改为通用文档处理平台
- `2_system_design.md`：继续定义检索升级与 `Knowledge Unit` 统一方案
- `document_ingestion_boundary.md`：只补齐两者之间此前默认存在、但尚未单独冻结的“文档接入与清洗边界”

### 2.3 当前边界判断

当前系统可以继续保持以下事实不变：

1. 主场景仍是 FAQ / 业务知识问答
2. 主链路仍是“提问 -> 检索 -> 回答 -> 返回”
3. 不把当前系统改成大而全平台
4. 扩展性仍只保留薄接口

但需要补充一条此前未单独冻结的边界：

**当输入超出“FAQ / 简单业务文档 / 结构相对规整文本”范围时，不应直接把原始文档送入检索链路，而应先进入文档清洗 / ingestion adapter。**

---

## 3. 为什么需要单独冻结该边界

当前 `1_system_design.md` 已明确：

- 当前输入对象主要是 FAQ 标准问答对、简单业务文档、结构相对规整的文本内容
- 当前离线入库链路只做基础解析、简单切块、基础索引构建
- 当前明确不做复杂版式分析、PDF 表格精准还原、重型数据治理流程与复杂离线任务编排

与此同时，`2_system_design.md` 又要求：

- FAQ 与 document chunk 最终统一映射为同一 `Knowledge Unit`
- 下游检索、证据抽取、citation、缓存与回滚都依赖该统一输入结构

因此，当前真实缺口并不在问答链路本身，而在于：

**原始文档如何被可靠地转换为下游真正可消费的知识输入。**

---

## 4. 总体边界

### 4.1 总体链路

```text
原始 FAQ / 原始文档
-> 文档接入判断
-> 直接入库
   或
-> ingestion / cleaning adapter
-> 标准化知识输入
-> 索引构建
-> FAQ / 文档检索
-> 回答生成
```

### 4.2 核心原则

1. 不是所有文档都应直接进入当前主链路
2. 文档清洗层是上游适配层，不是系统主脑
3. 下游检索与回答只消费“已被清洗并标准化后的知识输入”
4. 当前不追求全行业、全格式、全自动通吃
5. 当前先冻结边界，再决定内部是自建、半人工还是接第三方能力

---

## 5. 输入分级

### 5.1 A 类：可直接进入当前链路的输入

以下输入允许不经过独立清洗服务，直接进入当前轻量离线入库链路：

1. FAQ 标准问答对
2. Markdown / 纯文本制度文档
3. 标题层级清晰、正文规整的 Word 导出文本
4. 已人工整理过的 FAQ 列表或知识条目
5. 已具备稳定来源定位信息的简单 chunk 数据

判断标准：

- 版式噪音低
- 字段边界清晰
- 不依赖复杂表格恢复
- 不依赖 OCR 才能获取正文
- 可较低成本保留回源定位

### 5.2 B 类：必须先经过 ingestion / cleaning adapter 的输入

以下输入不应直接进入检索主链路：

1. 扫描件 PDF
2. 多栏、复杂版式 PDF
3. 表格为主的制度文档
4. 页眉页脚、附件、盖章、批注噪音较重的文档
5. 多版本制度混杂、时效不清的文档
6. 多来源导出、字段不统一的历史文档集合
7. 需要补齐访问范围、部门范围、有效期语义的原始材料

判断标准：

- 不做清洗就难以可靠切块
- 不做清洗就难以保留 citation 回源
- 不做清洗就难以补齐版本 / 生命周期 / 访问范围
- 不做清洗就会明显污染检索质量或证据可信度

### 5.3 C 类：当前阶段明确不承诺处理的输入

当前阶段不承诺以下类型可自动稳定接入：

1. 高度依赖视觉理解的复杂图文混排材料
2. 需要精确恢复跨页表格关系的文档
3. 大量扫描件 + 手写内容 + 多语混合材料
4. 需要跨系统长期自动同步治理的异构知识源
5. 强依赖复杂审批状态或个人态数据拼装的动态文档

结论：

**当前阶段的文档通用性是“弱通用”，不是“任意文档即插即用”。**

## 6. ingestion / cleaning adapter 的职责

### 6.1 负责什么

文档清洗 / ingestion adapter 负责：

1. 文档类型识别与接入判断
2. 基础去噪
3. 正文抽取
4. 标题层级与块边界恢复（在可行范围内）
5. 文档切块
6. 回源定位信息保留
7. 最小元数据补齐
8. FAQ / 文档向下游统一知识输入映射
9. 为下游索引构建提供稳定输入

### 6.2 不负责什么

文档清洗 / ingestion adapter 不负责：

1. 用户问题理解
2. Query Planner
3. 检索召回
4. Rerank
5. Answer Composer
6. 最终回答生成
7. 独立的工作流编排中心
8. 通用数据中台治理平台

### 6.3 当前允许的实现方式

当前边界只冻结职责，不冻结具体技术路线。允许包括：

1. 纯规则解析
2. OCR + 规则清洗
3. LLM 辅助结构抽取
4. 第三方文档解析能力接入
5. 半自动人工校验流程

结论：

**当前阶段先冻结“必须有这一层”，不强制冻结“这一层必须完全自研”。**

## 7. AI 在文档清洗中的使用边界

### 7.1 当前允许 AI 加速的环节

AI 可以用于加速以下环节：

1. 版面理解后的结构恢复
2. 标题与段落层级识别
3. FAQ 候选问答对抽取
4. 噪音段落识别
5. chunk 标题补全
6. 表格转文字摘要（仅在可接受误差范围内）
7. 初步业务域 / 文档类型 / 来源类型归类

### 7.2 当前不应把 AI 当作唯一真相来源的环节

以下环节不应只依赖自由生成：

1. 回源定位信息生成
2. 版本号、有效期、访问范围的关键业务字段确定
3. 高风险制度条款的最终结构化落盘
4. 影响 citation 回源能力的关键定位信息
5. 影响缓存失效与版本快照判断的关键字段

### 7.3 当前原则

AI 可以提升清洗速度，但不能替代关键字段的可追踪性与确定性。

结论：

**当前文档清洗可以利用 AI 快速清洗，但下游依赖的关键元数据仍必须具备确定性、回源能力与可复核性。**

## 8. 与 `1_system_design.md` 的衔接方式

### 8.1 不改主定位

`1_system_design.md` 继续保持：

- FAQ / 业务知识问答是唯一主场景
- 当前主链路仍以问答为中心
- 当前不做大而全平台化抽象

### 8.2 需要新增的衔接语义

`1_system_design.md` 不需要重写方向，但需要补充一句明确边界：

**当输入超出 FAQ、简单业务文档、结构相对规整文本范围时，原始文档不直接进入当前离线入库链路，而应先由文档清洗 / ingestion adapter 转换为可检索文本与最小回源元数据，再进入下游存储与检索流程。**

### 8.3 当前阶段的实现建议

当前阶段允许：

1. 保持 A 类输入直接入库
2. 将 B 类输入暂时标记为“需清洗后再接入”
3. 文档清洗能力可先以人工整理、半自动脚本或外部能力接入方式补齐

结论：

**`1_system_design.md` 只需要补边界，不需要改主系统定位。**

---

## 9. 与 `2_system_design.md` 的衔接方式

### 9.1 需要改写的默认假设

`2_system_design.md` 当前默认写法中，`解析原始输入 -> 转换为统一 Knowledge Unit` 过于压缩。

建议改写为：

```text
原始 FAQ / 原始文档
-> 文档接入判断
-> direct ingest
   或
-> ingestion / cleaning adapter
-> 标准化知识输入映射
-> 元数据补齐
-> question / answer 向量生成
-> 写入 knowledge_units_v1
```

### 9.2 `2_system_design.md` 的原则

1. Hybrid Retrieval 只处理“已被清洗且已标准化”的知识输入
2. Query Planner 不承担原始文档理解职责
3. Rerank / Evidence Extraction 不修复上游脏数据
4. Citation、版本控制、缓存失效都依赖上游正确输出的回源定位、版本与时效信息

### 9.3 实施顺序建议

在 `2_system_design.md` 的 Step 1 中，应先补齐：

1. 文档接入判断
2. ingestion / cleaning adapter 接口
3. 标准化知识输入映射逻辑
4. 默认值契约
5. 回填批次记录

而不是默认所有原始文档都能直接被“解析原始输入”一步安全吞掉。

---

## 10. 当前明确不做的内容

当前文档清洗边界说明明确不做：

1. 通用文档平台产品定义
2. 全行业、全格式、全自动稳定接入承诺
3. 独立的数据治理中台
4. 复杂工作流编排与多级审核平台
5. 对所有扫描件、表格、历史制度自动无误恢复的承诺
6. 独立的字段定义表与完整 `Knowledge Unit` 契约文档

结论：

**当前阶段卖点应是“把指定范围内的文档清洗成 OrionStack 可消费的知识输入”，而不是宣称“任意文档即插即用”。**

---

## 11. 最终结论

OrionStack 当前不需要改成通用文档产品。

更准确的边界应为：

1. 主系统继续是 FAQ / 业务知识问答系统
2. 文档清洗 / ingestion adapter 是上游适配层
3. 弱通用输入直接入库
4. 复杂文档先清洗再进入下游统一知识输入
5. 文档清洗层可以半产品化、可服务化、可替换

一句话收敛：

**OrionStack 当前最合理的演进，不是把问答系统改写成通用文档平台，而是在其上游冻结一层“文档接入与清洗边界”，把复杂文档转换为可检索、可引用、可控版本的标准化知识输入，再交给下游问答主链路处理。**
