# OrionStack 当前阶段系统设计 v1

## 1. 文档说明

### 1.1 文档目标

本文档用于重新定义 OrionStack 当前阶段的真实系统设计边界，作为后续代码实现与文档拆分的唯一基线。

这份文档只回答以下问题：

1. 当前系统到底是什么
2. 当前阶段到底做什么、不做什么
3. 当前最小可执行链路是什么
4. 当前模块边界如何划分
5. 哪些设计明确暂不采用

本文档不承担以下职责：

- 不描述远期平台化蓝图
- 不预埋复杂多场景扩展设计
- 不提前设计多 Agent 编排体系
- 不为了未来可能性而引入当前无必要复杂度

### 1.2 适用范围

本文档适用于 OrionStack 当前阶段的设计、开发、评审与文档整理。

当前阶段以 **FAQ / 业务知识问答** 为唯一主场景，所有设计均围绕这一主场景收敛。

### 1.3 文档原则

本文档遵循以下原则：

1. 只写当前真实需要落地的设计
2. 只保留近期会进入代码的边界与结构
3. 不把未来架构复杂度提前搬入当前系统
4. 先保证主链路稳定，再讨论扩展性
5. 扩展性只保留接口位，不保留重型实现

---

## 2. 当前系统定位

### 2.1 一句话定位

OrionStack 当前阶段是一个 **面向 FAQ / 业务知识问答场景的轻量应用系统**，目标是用最小复杂度实现稳定的“提问 -> 检索 -> 回答”主链路。

### 2.2 当前系统是什么

当前系统是：

- 一个以问答为核心的业务应用
- 一个以 FAQ / 文档内容检索为基础的数据驱动系统
- 一个优先保证稳定性、可控性和低复杂度的实现
- 一个以轻量路由决策和轻量检索链路为主的系统

### 2.3 当前系统不是什么

当前系统不是：

- 通用企业 AI 平台
- 多场景统一编排底座
- 复杂 Agent 运行时
- 图执行工作流平台
- 大而全知识中台
- 统一意图中台
- 为未来所有场景预留完备抽象的基础设施

### 2.4 当前设计取向

当前阶段的设计取向不是“先做大框架再填业务”，而是：

- 先做最小可用主链路
- 先做稳定问答结果
- 先做可控的数据流
- 先做清晰模块边界
- 未来确有需要时再逐步替换局部实现

---

## 3. 当前阶段范围

### 3.1 当前要做的内容

当前阶段只做以下内容：

1. 接收用户问题
2. 对请求做轻量路由判断
3. 执行 FAQ / 文档检索
4. 基于检索结果生成回答
5. 返回回答与必要引用信息
6. 保留最小必要的请求记录与结果记录
7. 为后续替换局部能力保留最小接口边界

### 3.2 当前明确不做的内容

当前阶段明确不做以下内容：

1. 不做 LangGraph 图执行
2. 不做复杂流式工作流编排
3. 不做 LlamaIndex 知识框架接入
4. 不做重型统一意图层
5. 不做复杂 JSON 工具规划
6. 不做多 Agent 协作
7. 不做复杂工具编排中心
8. 不做大而全平台化抽象
9. 不做为未来多场景预埋的大量框架层
10. 不做脱离当前业务的“中台化”设计
11. 不做细粒度的行级/文档级权限控制（RBAC/ABAC）与独立的权限管理系统。

### 3.3 当前范围边界的核心判断

当前系统的核心任务只有一个：

**让 FAQ / 业务知识问答主链路稳定可用。**

只要某个设计不能直接提升这条主链路的稳定性、可控性或维护成本表现，就不应在当前阶段进入系统。

## 4. 核心执行链路

### 4.1 当前主链路

当前系统的最小主链路定义如下：

```text
用户问题
-> 路由判断（薄）
-> FAQ / 文档检索
-> 回答生成
-> 返回结果
```

这是当前唯一必须稳定的执行链路。

该链路用于表达当前系统的概念主链路。

在实际运行中，允许在进入主链路前挂接少量前置步骤，例如输入归一化、基础安全校验与 FAQ 缓存匹配，但这些步骤不改变系统的核心执行目标，仍服务于“提问 -> 检索 -> 回答 -> 返回”的主路径。

### 4.2 链路说明

#### 第一步：接收用户问题

系统接收前端传入的问题文本及必要上下文。

当前阶段允许前端通过固定提问范式、示例问题或快捷提问入口，对用户输入做轻量引导与归一化，以降低输入随机性并提升 FAQ / 检索链路命中率。

这类输入引导属于轻量输入约束，不构成复杂意图规划，也不构成独立的对话引导系统。

当前阶段不要求复杂多轮意图规划，不要求工具计划生成，不要求复杂结构化执行计划。

#### 第二步：路由判断（薄）

系统对请求做轻量级判断，只回答以下问题：

1. 当前请求是否属于 FAQ / 知识问答范围
2. 当前请求是否可以直接进入检索问答链路
3. 当前请求是否需要进入兜底路径

这一层只做“是否走问答主链路”的判断，不承担复杂规划职责。

#### 第三步：FAQ / 文档检索

系统根据问题文本或轻量改写后的查询词执行检索。

当前阶段允许采用轻量实现，例如：

- SQLite FTS
- 简单向量检索
- pgvector
- 自定义检索服务

检索层的目标是返回足够可用的候选内容，不引入额外框架复杂度。

#### 第四步：回答生成

系统基于检索结果调用模型或模板逻辑生成回答。

当前阶段可使用本地小模型，但必须控制其职责：

- 小模型负责回答生成或简单分类
- 小模型不负责复杂结构化意图路由
- 小模型不负责多工具计划生成
- 小模型不负责高风险复杂决策

#### 第五步补充：最小 citation 返回结构

当前阶段如返回 `citations`，前后端应尽量遵循最小一致结构。

建议单条 citation 至少包含以下字段：

- `citation_id`：引用标识
- `source_label`：来源展示名称
- `source_locator`：来源定位信息，例如 `source_url`、`file_path`、`page_number`、`paragraph_id` 或等价定位字段
- `snippet`：最小引用片段

当前阶段不要求建设复杂引用协议，但必须避免前后端对 citation 结构各自定义，导致展示与跳转能力不一致。

结论：

**当前 citations 除具备回源能力外，也应具备最小一致的返回结构。**

#### 4.2.1 最小对外结果状态

为了避免前端或调用方依赖回答文本自行猜测系统状态，当前阶段建议对外冻结最小结果状态字段，例如：

- `ok`：正常回答
- `refused`：命中安全边界或明确不能回答
- `fallback`：未进入标准 FAQ 回答路径，进入统一兜底
- `system_error`：系统异常或不可恢复错误

当前阶段不要求建设复杂统一错误模型，但建议至少保证调用方能够区分：

1. 正常回答
2. 安全拒答
3. 无依据或低置信度兜底
4. 系统异常

结论：

**当前对外结果至少应具备最小状态分类，避免仅依赖 `answer_text` 承担全部语义。**

### 4.3 关于 Streaming 的当前结论

当前阶段允许保留流式输出能力，但需要明确：

**流式输出只是响应输出方式，不构成引入图执行框架的理由。**

也就是说：

- 可以实现 SSE / 流式 token 输出
- 但不因此引入 LangGraph 或复杂工作流状态机
- 流式能力应作为回答生成层的输出能力，而不是系统架构中心

## 5. 模块划分

### 5.1 模块划分原则

当前阶段模块划分只服务于主链路，不为了宏大架构叙事而增加层次。

模块划分原则如下：

1. 只保留当前必要模块
2. 模块命名尽量贴近实际职责
3. 一个模块只解决一类问题
4. 模块之间通过最小接口连接
5. 不为了“看起来先进”而过度分层

### 5.2 当前必要模块

#### 5.2.1 前端页面层

职责：

- 接收用户输入
- 展示回答结果
- 展示引用信息
- 提供最小交互页面
- 提供最小反馈交互（如点赞 / 点踩）
- 提供固定提问范式、示例问题或快捷提问入口，用于轻量引导用户输入
- 提供最小 Debug 模式入口，用于开发态展示关键链路信息
- 支持复制当前调试上下文（如 `trace_id`、`normalized_query`、`retrieved_chunks`、`final_prompt`）

不负责：

- 不负责业务决策
- 不负责检索逻辑
- 不负责模型调用
- 不负责复杂评估体系
- 不负责复杂对话引导系统或独立表单编排系统
- 不负责独立调试平台建设

#### 5.2.2 API 层

职责：

- 接收请求
- 校验输入
- 调用后端服务
- 返回同步或流式结果
- 接收最小反馈请求并写入后端记录
- 在请求入口生成 `trace_id`，并通过请求上下文在整个调用链中透传
- 支持开发态 Demo 模式入口与最小调试信息透传

不负责：

- 不负责复杂路由编排
- 不负责直接实现检索细节
- 不负责复杂模型策略决策
- 不负责重型评估平台逻辑
- 不负责复杂环境编排与多级反向代理链路

当前阶段建议采用轻量方式贯穿 `trace_id`，例如 `contextvars` 或等效机制，以保证即使不引入复杂工作流框架，也能通过同一追踪标识串联输入、路由、检索、生成与反馈记录。

#### 5.2.3 路由决策层

职责：

- 对请求进行轻量判断
- 给出当前请求的最小路由决定
- 为检索层提供稳定输入

不负责：

- 不负责复杂意图规划
- 不负责多工具调度
- 不负责复杂实体抽取
- 不负责生成重型执行计划

#### 5.2.4 检索层

职责：

- 接收查询词
- 执行 FAQ / 文档检索
- 返回候选内容与必要元数据
- 为回答生成层提供可消费输入

不负责：

- 不负责前端展示
- 不负责复杂工作流控制
- 不负责未来知识平台抽象

#### 5.2.5 回答生成层

职责：

- 基于检索结果生成最终回答
- 组织最小必要引用信息
- 输出最终回答内容

不负责：

- 不负责复杂工具编排
- 不负责图状态管理
- 不负责复杂意图识别

#### 5.2.6 数据存储层

职责：

- 存储 FAQ / 文档数据
- 存储必要索引数据
- 存储最小必要日志或记录
- 存储最小必要反馈数据
- 为向量数据或检索索引记录必要版本信息，例如 `embedding_model_version`

不负责：

- 不负责业务控制逻辑
- 不负责模型推理
- 不负责路由判断

当前阶段不要求复杂索引治理系统，但必须避免在升级 embedding 模型后继续无感使用旧版本向量，导致检索结果整体失真而难以排查。

## 6. 关键设计决策

### 6.1 当前不使用 LangGraph

当前阶段不引入 LangGraph。

原因如下：

1. 当前主链路不具备复杂图执行特征
2. 当前业务不需要多状态持久化流程
3. 当前没有明确的中断 / 恢复 / 多分支编排需求
4. 引入图执行框架会显著增加理解成本与维护成本
5. 当前收益不足以覆盖框架复杂度

结论：

**当前用普通服务调用链即可，不引入图执行工作流框架。**

### 6.2 当前不使用 LlamaIndex

当前阶段不引入 LlamaIndex。

原因如下：

1. 当前 FAQ / 文档问答链路可以由自研轻量检索实现
2. 当前核心问题不是“知识框架能力不足”，而是“主链路应保持简单可控”
3. 引入额外知识框架会增加排错路径与抽象负担
4. 当前检索需求尚不足以支撑引入重型知识框架

结论：

**当前优先采用自研轻量检索链路，而不是引入知识框架。**

### 6.3 当前不建设重型统一意图层

当前阶段不建设重型统一意图层。

原因如下：

1. 当前只有单一主场景，复杂统一路由收益不足
2. 当前 1B/8B 小模型不适合承担复杂结构化意图规划
3. 小模型输出复杂 JSON 路由计划不稳定，容易使系统脆弱
4. 当前系统需要的是“薄决策”，不是“意图中台”

结论：

**当前只保留轻量路由决策接口，不建设重型统一意图层。**

### 6.4 当前不让小模型承担复杂规划职责

当前阶段，小模型只承担以下职责之一：

- 简单分类
- 简单回答生成
- 简单查询改写

当前阶段，小模型不承担以下职责：

- 复杂 JSON 路由输出
- 多工具计划生成
- 稳定实体抽取总控
- 复杂执行计划生成
- 系统级核心编排职责

结论：

**小模型只做其稳定擅长的事，不承担系统中最脆弱、最关键的复杂控制职责。**

### 6.5 当前只保留薄接口，不保留重型未来实现

当前阶段允许为未来预留接口位，但不允许把未来完整架构提前引入当前系统。

可以保留：

- 可替换的路由接口
- 可替换的检索实现
- 可替换的模型调用实现

不保留：

- 未来完整统一中台实现
- 多层复杂抽象骨架
- 不进入当前代码的重型设计

## 7. 最小接口边界

### 7.1 设计目标

最小接口边界的目标不是追求“完美架构”，而是实现：

1. 当前代码足够简单
2. 当前模块足够解耦
3. 未来局部替换不推翻主链路

### 7.2 当前路由决策对象

当前建议仅保留最小决策对象，例如：

```python
from pydantic import BaseModel
from typing import Literal

class IntentDecision(BaseModel):
    route: Literal["faq_qa", "fallback"]
    confidence: float
    query_for_search: str
```

### 7.3 当前路由层输入输出边界

输入：

- 用户原始问题
- 请求级最小上下文（可选，仅供路由协调层使用）

说明：

- 路由协调层可接收请求级最小上下文。
- 具体 Parser 的输入约束以 7.6.1 为准，不得私自扩大依赖范围。

输出：

- 当前请求走哪条最小路径
- 一个可供检索使用的查询词
- 一个可供兜底判断的置信度

路由层不输出：

- 复杂工具计划
- 多级任务图
- 长 JSON 结构
- 下游执行细节

### 7.4 检索层输入输出边界

输入：

- query_for_search
- 可选过滤条件

输出：

- 命中的 FAQ / 文档内容
- 最小必要元数据
- 可供回答生成层消费的候选结果

检索层不关心：

- 请求来自哪个解析器
- 是否未来会接更强模型
- 是否未来会接复杂工作流

### 7.5 回答生成层输入输出边界

输入：

- 用户问题
- 检索结果

输出：

- answer
- citations（如有）
- 最小元信息

回答生成层不关心：

- 当前路由是规则做的还是模型做的
- 未来是否会切换高级解析器
- 是否接入复杂工具系统

### 7.6 路由解析器输入输出契约

为了保证当前薄路由层未来可以平滑替换内部实现，所有路由解析器必须遵循统一的输入输出契约。

#### 7.6.1 输入契约

当前阶段，Parser 只允许依赖最小输入：

- `raw_query`
- 固定路由说明文本（可选）

当前阶段不允许 Parser 私自依赖以下输入：

- 多轮历史对话
- 复杂 session state
- 检索结果预读
- 外部工具返回值
- 特定实现私有上下文

结论：

**当前 Parser 输入必须保持最小化与标准化，避免未来不同 Parser 之间产生上下文依赖不一致。**

#### 7.6.2 输出契约

无论当前使用规则、1B/8B 小模型，还是未来更强模型，Parser 对外都必须统一输出 `IntentDecision`：

```python
from pydantic import BaseModel
from typing import Literal

class IntentDecision(BaseModel):
    route: Literal["faq_qa", "fallback"]
    confidence: float
    query_for_search: str
```
输出约束如下：

route 只能使用固定枚举值
confidence 对外统一映射到 0.0 - 1.0 区间，但当前阶段不要求其具备严格数学概率意义
confidence 允许来源于规则映射、模型分类结果或等级映射，其作用是支持路由比较、阈值判断与观测分析
query_for_search 必须始终为字符串
不允许输出额外结构化计划对象作为下游依赖

当前阶段允许将内部路由判断粗分为以下逻辑层级：

Certain：规则强命中
High：模型分类清晰且符合预期
Low：进入 fallback

结论：

当前 confidence 是标准化后的逻辑置信度接口，而不是严格概率承诺。下游模块只依赖统一 DTO，不依赖具体 Parser 实现。

## 8. 当前推荐实现方式

### 8.1 路由决策推荐实现

当前推荐采用以下顺序：

```text
规则判断
-> 轻量模型简单分类（可选）
-> fallback
```

其中：

- 规则判断优先
- 小模型只做简单分类
- 小模型输出尽量限制为少量标签
- Python 代码负责把结果装配成稳定结构

### 8.2 当前推荐检索实现

当前推荐优先使用轻量可控实现，例如：

- SQLite FTS
- pgvector
- 自定义 FAQ 检索服务
- 轻量向量检索

具体选型以实现复杂度、可控性、排错成本为准。

#### 8.2.1 检索最低可回答边界

当前阶段，检索命中并不自动等于可以生成回答。

为了降低“无依据自由生成”的风险，当前阶段建议增加最小可回答边界，例如：

1. 当检索结果相似度低于最低阈值时，直接进入拒答或 fallback。
2. 当没有可用候选内容或引用依据时，不进入自由生成。
3. 当最高命中结果低于最低可回答阈值时，应将其视为“未命中”，不向生成层传递伪上下文。
4. 当前阶段优先遵循“无足够依据，进入拒答或 fallback”的原则。

当前阶段不要求复杂检索评估体系，但必须避免把弱命中结果直接包装为高可信回答，也必须避免把似是而非的检索片段传给生成层诱发幻觉续写。

### 8.3 当前推荐回答生成实现

回答生成可以基于：

- 模型生成
- 模板拼接
- 混合方式

但必须满足：

1. 输入来源明确
2. 结果路径可追踪
3. 不依赖复杂工作流框架
4. 不让模型承担其不稳定的高阶规划职责
5. 必须配置明确的输出截断策略，避免小模型重复输出、越界续写或泄露 Prompt 后续内容
6. 在 FAQ 回答生成场景下，应优先采用低随机性参数，避免同一问题在短时间内产生明显语义漂移

当前阶段建议至少具备以下工程约束：

- `max_tokens`：限制单次回答最大输出长度
- `stop_words` / `stop_sequences`：用于阻断模型继续吐出模板尾部、角色标识或无关续写内容
- FAQ 回答生成场景下，`temperature` 应默认保持在接近 0 的低随机性范围
- 流式输出场景下应具备明确的结束条件，避免模型持续重复生成

当前阶段不要求复杂生成控制平台，但必须避免把回答生成层变成不受约束的自由续写过程。

### 8.4 路由决策的降级与保护

#### 8.4.1 目标

当前阶段允许使用小模型参与轻量路由判断，但必须避免小模型不稳定导致主链路失效或兜底流量异常放大。

因此，当前路由决策必须具备最小降级与保护机制。

#### 8.4.2 置信度阈值配置化

当前阶段，路由置信度阈值不得写死在代码中，必须通过配置项控制，例如：

- `CONFIDENCE_THRESHOLD`

该阈值用于判断当前 Parser 输出是否足够可信。

当前阶段要求：

- 阈值可通过配置快速调整
- 不要求复杂动态控制平台
- 但必须避免把阈值硬编码进核心逻辑

#### 8.4.3 当前推荐降级链路

当前推荐的路由决策链路如下：

```text
规则判断
-> 小模型简单分类（可选）
-> confidence check
-> 规则兜底匹配
-> fallback
```

其含义为：

1. 优先使用确定性规则判断
2. 小模型只做简单分类
3. 当小模型置信度不足时，不立即进入高成本路径
4. 先尝试一次轻量规则兜底
5. 规则仍无法处理时，再进入统一 fallback

#### 8.4.4 当前明确不做的内容

当前阶段明确不做：

- 复杂策略引擎
- 多级熔断中心
- 动态路由编排平台
- 大规模在线策略调优系统

结论：

**当前降级机制只为防止小模型不稳定放大系统成本，不扩展为独立策略系统。**

#### 8.4.5 当前建议冻结的 fallback_reason 最小枚举

为了保证 fallback 路径可观测、可排错，当前阶段建议将 `fallback_reason` 收敛为最小固定枚举，例如：

- `low_confidence`
- `guardrail_blocked`
- `rule_no_match`
- `no_retrieval`
- `system_error`

当前阶段不要求覆盖所有未来场景，但要求避免自由文本原因码扩散。

结论：

**当前 fallback_reason 应尽量收敛为固定枚举，避免日志与实现语义漂移。**

#### 8.4.6 非法输出的默认降级策略

当前阶段允许使用小模型参与轻量路由判断，但不允许把模型输出格式正确性当作系统前提。

因此，当前阶段必须具备最小非法输出兜底策略：

1. 当路由模型输出为空、标签非法、字段缺失或不符合预期格式时，代码层必须捕获异常或解析失败。
2. 一旦解析失败，不做二次猜测，不把非法输出继续向下游传播。
3. 解析失败后的默认路径为统一 `fallback`，并记录相应的 `fallback_reason`。

当前阶段不要求复杂输出修复器或二次纠错模型，但必须避免让非法路由输出直接破坏主链路稳定性。

结论：

**当前路由模型的非法输出必须默认导向 fallback，而不是让系统依赖模型格式稳定性。**

## 9. 支撑性链路设计

### 9.1 设计目标

当前阶段的系统设计虽然以在线问答主链路为中心，但为了保证系统能够稳定运行、低成本维护并支持后续迭代，仍需补齐少量必要的支撑性链路。

这些支撑性链路的目标不是引入新框架，而是形成最小闭环，确保系统不仅能“跑通”，还能“稳健且可迭代”。

当前阶段只补充以下 7 类支撑能力：

1. 轻量离线数据入库链路
2. 高频 FAQ 拦截缓存
3. 基础安全与拒答边界
4. 轻量反馈回流机制
5. 固定提问范式与输入引导
6. 核心 Prompt 与阈值的配置化管理
7. 数据隔离与前置过滤权限接口预留
   
这些能力均遵循同一原则：

- 只做当前主链路必需的最小实现
- 不扩展为独立平台或重型子系统
- 不为了未来可能需求提前引入复杂架构

### 9.2 轻量离线数据入库链路

#### 9.2.1 目标

系统必须定义数据如何进入系统并变成可检索状态。

当前阶段支持的输入对象包括：

- FAQ 标准问答对
- 简单业务文档
- 结构相对规整的文本内容

#### 9.2.2 当前最小入库链路

当前推荐的离线数据链路如下：

```text
原始 FAQ / 文档
-> 基础解析
-> 简单文本切块（如需要）
-> 向量化或全文索引构建
-> 入库到 SQLite FTS / pgvector / 轻量检索存储
```
##### 9.2.2.1 最小回源元数据要求
当前阶段，离线数据入库不仅要让内容变得可检索，还必须为后续引用展示保留最小回源能力。

因此，当前入库链路应尽量为每个 FAQ 条目或文档 chunk 保留以下最小元数据之一或其组合：

- `source_url`
- `file_path`
- `document_id`
- `page_number`（如适用）
- `paragraph_id` 或 `chunk_id`
- 文档内定位所需的最小偏移信息（如适用）

当前阶段不要求建设复杂引用管理系统，但必须避免只存 chunk 文本而完全失去原始来源定位能力。

结论：

**当前引用信息必须具备最小回源元数据，确保前端展示的 citations 可以指向原始 FAQ 或文档位置。**

#### 9.2.3 当前只做的内容

当前阶段只做：

1. 基础文本解析
2. 简单切块
3. 基础索引构建
4. FAQ 问答对导入
5. 简单文档内容导入

#### 9.2.4 当前明确不做的内容

当前阶段明确不做：

1. 复杂版式分析
2. PDF 表格精准还原
3. 自动知识图谱抽取
4. 多源实时同步
5. 重型数据治理流程
6. 复杂离线任务编排系统

结论：

**当前离线链路只服务于“让内容变得可检索”，不扩展成知识加工平台。**

### 9.3 高频 FAQ 拦截缓存

#### 9.3.1 目标

FAQ 场景天然存在大量重复问题或高频近似问题。

如果每次请求都进入“检索 -> 生成”链路，会增加延迟和资源消耗，也会让主链路不必要地变重。

因此，当前阶段应在主链路前增加一层极轻量缓存拦截。

#### 9.3.2 当前缓存位置

当前建议将缓存拦截放在：

```text
用户问题
-> 路由判断（薄）
-> FAQ 缓存匹配
-> 检索
-> 回答生成
```

#### 9.3.3 当前缓存策略

当前阶段仅允许以下缓存方式：

1. 标准 FAQ 问答对精确匹配
2. 高阈值的轻量近似匹配
3. 命中后直接返回标准答案

#### 9.3.4 当前最小缓存失效边界

当前阶段虽然不建设复杂缓存治理系统，但仍需定义最小失效边界。

当前建议至少满足以下规则：

1. 当 FAQ 标准问答内容更新时，关联缓存应失效。
2. 当检索语料或索引版本发生明显变化时，可按版本号使缓存失效。
3. 当前阶段允许采用简单清理策略，不要求复杂 TTL 平台或自动治理体系。

结论：

**当前缓存必须具备最小失效边界，避免旧答案长期静默污染主链路。**

#### 9.3.5 当前明确不做的内容

当前阶段明确不做：

1. 通用多级缓存架构
2. 复杂语义缓存平台
3. 自动缓存治理系统
4. 大规模动态失效策略体系
5. 跨场景统一缓存中台

结论：

**当前缓存的目标只是拦截高频 FAQ，不把缓存设计扩展成独立系统。**

### 9.4 基础安全与拒答边界

#### 9.4.1 目标

系统不仅需要处理“答不出来”的情况，也必须处理“不能回答”的情况。

即使当前系统聚焦内部 FAQ / 业务知识问答，仍需定义最小安全边界，避免模型被诱导输出不应回答的内容。

#### 9.4.2 当前安全边界位置

当前建议将基础安全校验放在主链路前部，即：

```text
用户问题
-> 基础安全校验
-> 路由判断（薄）
-> FAQ 缓存匹配
-> 检索
-> 回答生成
```

或与路由判断合并实现，但逻辑边界必须清晰。

#### 9.4.3 护栏设计原则：输入一致性为先

为了使当前轻量级安全护栏稳定生效，API 接入层必须对用户输入执行最小必要的输入一致性约束。

该约束的目标不是增强系统智能，而是降低输入噪声、避免规则绕过，并为后续安全校验、缓存匹配、路由判断与检索提供更稳定的输入基础。

当前阶段至少包括以下两类约束：

1. **长度限制**  
   必须为用户输入设置明确的最大长度阈值（如 `MAX_QUERY_LENGTH`），超限请求直接拒绝或返回标准提示话术。  
   该阈值必须通过配置项控制，不得硬编码在业务逻辑中。

2. **字符清洗与归一化**  
   在进入后续规则校验、缓存匹配、路由判断与检索前，系统必须生成规范化后的输入文本，例如：
   - 去除不可见字符
   - 规范化换行、空格与重复分隔符
   - 对 HTML 标签做安全清洗
   - 对 Markdown / 代码块做轻量归一化
   - 保留核心文本语义，不做破坏性删除

当前阶段要求同时保留：

- `raw_query`：原始输入，用于审计、排查与观测
- `normalized_query`：归一化输入，用于后续安全校验与主链路处理

结论：

**当前输入一致性约束属于轻量 Guardrails 的前置基础，不扩展为独立输入治理系统。**

#### 9.4.4 当前允许的实现方式

当前阶段只允许轻量实现方式，例如：

1. 敏感词或规则拦截
2. 基础正则判断
3. 小模型 system prompt 中的严格拒答约束
4. 命中后直接返回标准拒答话术
5. API 接入层的输入长度限制与字符归一化

#### 9.4.5 当前明确不做的内容

当前阶段明确不做：

1. 独立风控大模型
2. 独立安全策略编排平台
3. 复杂内容审核工作流
4. 多级风险评分系统
5. 复杂对抗防御体系

结论：

**当前安全边界只负责最小必要拒答，不扩展为独立安全系统。**

#### 9.4.6 固定提问范式与输入引导

##### 9.4.6.1 目标

当前阶段允许通过固定提问范式、示例问题和快捷提问入口，对用户输入进行轻量约束与引导。

该设计的目标是：

1. 降低用户输入随机性
2. 提升 FAQ / 检索链路命中率
3. 提升高频问法缓存命中率
4. 降低小模型路由波动
5. 以更低成本减少部分越界输入与无效输入

##### 9.4.6.2 当前允许的实现方式

当前阶段只允许轻量实现方式，例如：

1. 前端展示固定示例问题
2. 提供按主题分类的快捷提问入口
3. 提供少量固定问句模板，例如：
   - 如何申请 X
   - 在哪里查看 X
   - X 的流程是什么
   - X 失败后怎么处理
4. 对用户输入做轻量归一化，例如去掉冗余语气词、保留核心关键词
5. 在提交前提示用户尽量使用单主题、直接问题表达

##### 9.4.6.3 当前设计边界

该能力属于轻量输入引导，不属于复杂意图系统。

其作用是帮助用户更容易进入当前 FAQ / 知识问答主链路，而不是替代检索、路由或回答生成。

##### 9.4.6.4 当前明确不做的内容

当前阶段明确不做：

1. 复杂多轮提问引导系统
2. 动态表单式问答编排
3. 基于模型的输入教育代理
4. 独立的用户行为纠正系统
5. 重型输入治理平台

结论：

**当前固定提问范式只作为轻量 Guardrails 与输入归一化补充，不扩展为独立交互系统。**


### 9.5 轻量反馈回流机制

#### 9.5.1 目标

当前阶段的日志与记录不仅用于排错，也用于为未来优化提供真实依据。

如果没有最小反馈回流，后续关于检索质量、模型效果、缓存命中价值以及架构升级必要性的判断都将缺乏数据支撑。

#### 9.5.2 当前前端交互要求

当前建议前端提供最简单的反馈交互，例如：

- 点赞
- 点踩

不要求当前阶段引入复杂评价组件。

#### 9.5.3 当前后端记录要求

当前阶段建议将记录字段分为“核心必记字段”和“扩展观测字段”，以保证最小数据闭环，同时避免记录结构过重或语义重复。

##### （1）核心必记字段

- `trace_id`：请求追踪标识，用于串联日志、反馈与排错。
- `raw_query`：用户原始问题文本。
- `retrieved_chunk_ids`：检索命中的候选内容或 chunks 标识列表，默认优先记录 ID，不要求默认落全文。
- `answer_text`：最终返回给用户的回答文本。
- `feedback_label`：用户反馈结果，如 `up` / `down`。
- `token_input`：输入 Token 数，用于评估调用成本与模型负载。
- `token_output`：输出 Token 数，用于评估调用成本与回答长度。
- `total_latency_ms`：整体请求总耗时。

##### （2）扩展观测字段

如系统已有会话或请求记录机制，也可附带：

- `session_id`：所属会话标识。
- `created_at`：请求时间戳。
- `router_used`：本次请求实际使用的路由器或解析器名称。
- `route_result`：最终路由结果，如 `faq_qa` / `fallback`。
- `raw_confidence`：路由模型原始置信度。
- `threshold_used`：本次判定使用的置信度阈值。
- `cache_hit`：是否命中缓存。
- `fallback_reason`：进入 fallback 的原因。
- `response_status`：最终对外结果状态，如 `ok` / `refused` / `fallback` / `system_error`
- `input_mode`：本次输入来源方式，如自由输入、示例点击或固定模板生成。
- `question_template_used`：命中的固定提问范式或模板标识（如有）。
- `raw_query_length`：原始输入长度，用于观察是否经常出现超长输入。
- `normalized_query_length`：归一化后输入长度，用于观察输入清洗影响。
- `first_token_latency_ms`：首字延迟，仅在流式生成场景下记录。
- `router_prompt_version`：当前路由 Prompt 或路由规则版本标识。
- `answer_prompt_version`：当前回答生成 Prompt 版本标识。
- `config_version`：当前阈值与策略配置版本标识。
- `normalized_query`：归一化后的输入文本，用于观察输入清洗后的实际查询内容。
- `retrieved_chunk_scores`：检索候选内容对应的相似度或排序分数（如适用）。
- `final_prompt`：最终发送给模型的 Prompt 文本或其可调试版本（开发态可记录，生产态可按需关闭或脱敏）。
- `debug_bundle_id`：当前调试上下文的标识，用于前端一键复制或回放。
- `demo_mode_used`：标记本次请求是否运行于 Demo 模式。



当请求未实际调用模型时，相关 token 字段允许为 0 或空值。

##### （3）当前记录设计原则

当前阶段的记录设计遵循以下原则：

1. 默认优先记录可分析、可观测、可追踪的最小字段集合。
2. 内容类字段与观测类字段分开定义，避免语义混杂。
3. 不因记录需求而把日志系统扩展为重型评测平台。
4. 字段命名统一使用稳定的 snake_case 风格。
5. 开发态允许记录最小可视化调试字段，但应避免默认把调试日志扩展为生产环境重负载记录体系。

##### （4）Prompt 签名与可回溯约束

当前阶段，`router_prompt_version`、`answer_prompt_version` 与 `config_version` 不应只是展示性标识，而应具备最小可回溯能力。

当前建议至少满足以下要求：

1. `router_prompt_version` 与 `answer_prompt_version` 应能映射到不可变版本标识。
2. 该标识可采用 Git Commit ID、内容哈希或等价签名机制实现。
3. 当用户反馈“效果变差”或出现行为漂移时，应能通过版本标识回溯当时生效的 Prompt 与配置内容。

当前阶段不要求建设复杂 Prompt 管理平台，但必须避免版本号存在而无法定位真实内容的情况。

结论：

**当前 Prompt 版本字段必须具备最小可回溯能力，而不是仅作为展示标签存在。**

##### （5）调试信息脱敏边界

当前阶段允许在开发环境中记录最小调试信息，但必须明确其脱敏与环境边界：

1. `final_prompt`、`retrieved_chunks`、`answer_text` 等字段在开发态可记录完整版本，用于调试。
2. 非开发态默认不记录完整 `final_prompt`，如需记录，应采用脱敏、摘要或显式开关方式。
3. 如 `user_query`、`answer_text` 或 chunk 内容可能包含敏感信息，应优先最小化展示与最小化存储。
4. 调试便利性不得凌驾于正式环境的最小暴露原则之上。

结论：

**当前调试信息应服务于开发效率，但必须具备最小脱敏边界与环境约束。**



#### 9.5.4 当前反馈机制的用途

当前阶段的反馈与记录机制，主要服务于以下目的：

1. 排查错误回答与异常链路，定位问题发生在输入、路由、缓存、检索、生成还是拒答边界。
2. 发现 FAQ 缺口与高频问题，判断哪些问题应沉淀为标准问答对或固定提问范式。
3. 评估检索质量，观察检索命中内容是否足以支撑最终回答。
4. 评估缓存价值，判断高频问题是否应优先走缓存拦截而不是重复进入检索与生成链路。
5. 观察路由决策效果，评估不同路由器、置信度阈值与降级策略是否合理。
6. 观察输入治理效果，判断固定提问范式、输入归一化与长度限制是否有效降低无效输入与越界输入。
7. 评估系统成本与性能，结合 token 与时延数据判断当前实现是否仍满足轻量、可控、可维护的目标。
8. 为后续是否升级 embedding、检索策略、路由决策或安全护栏提供真实依据。
9. 评估不同 Prompt、阈值与配置版本的效果差异，为后续调整提供对照依据。

结论：

**当前反馈机制的目标，是建立最小可观测、可排错、可迭代的数据闭环，而不是扩展为独立评测平台。**

#### 9.5.5 当前明确不做的内容

当前阶段明确不做：

1. 重型评测平台
2. 自动标注平台
3. 在线 AB 测试平台
4. 复杂数据飞轮平台化建设
5. 大规模反馈运营体系

结论：

**当前反馈回流只建立最小数据闭环与最小路由观测点，不扩展为独立评估系统。**


### 9.6 提示词与阈值的配置管理边界

#### 9.6.1 目标
避免将核心策略硬编码在代码中导致频繁发版，但绝不建设过重的配置管理中台。

#### 9.6.2 当前只做的内容
核心 Prompt（路由、生成、兜底、风控）和核心参数（阈值、Top-K）必须从业务代码中抽离，维护在轻量的配置文件（如 yaml / json）或环境变量中，支持随服务重启或热加载更新。

当前阶段在开发环境中建议支持最小 Prompt 热重载能力：

1. `prompts/` 目录中的 Prompt 文件修改后，可通过热重载或最小重载机制快速生效。
2. 开发者修改 Prompt 后，不应要求完整重启所有服务才能验证效果。
3. 该能力仅服务于本地开发体验优化，不构成复杂 Prompt 运行时编排系统。

#### 9.6.3 当前明确不做的内容
坚决不做独立的 Prompt 编排管理后台、不做可视化的 Prompt 调试沙箱、不做复杂的 Prompt 多版本灰度发布系统。
当前阶段也不建设复杂的 Prompt 在线调试平台或运行时可视化编排界面。

#### 9.6.4 配置优先级与生效规则

为了避免开发者在本地开发或调试过程中对“配置是否生效”产生歧义，当前阶段建议冻结最小配置优先级规则。

当前建议优先级如下：

1. 环境变量
2. 本地配置文件（如 yaml / json）
3. 内置默认值

当前阶段同时约束：

- 开发态热重载仅作用于开发环境
- 生产态以显式配置加载结果为准
- 当配置冲突时，应优先遵循更高优先级来源
- 关键配置变更应可通过 `config_version` 或等价字段进行观测

结论：

**当前配置行为必须具备最小优先级规则，避免因配置来源不清导致调试与运行结果不一致。**

### 9.7 数据隔离与权限预留边界 (RBAC Readiness)

#### 9.7.1 目标
未来本系统的权限控制将顺延自既有老系统（如 OA、ERP），OrionStack 不会作为权限源，而是作为权限执行节点（Policy Enforcement Point）。

#### 9.7.2 当前预留的边界设计
1. **数据存储预留**：向量/索引表中必须包含 `metadata` (JSON) 或特定标识字段，V1 阶段可默认全量开放或写入基础级隔离标识（如 `tenant_id`）。
2. **检索前置过滤预留**：核心检索模块 `retriever.search()` 必须设计接收 `filters` 参数的接口。明确采用**前置过滤（Pre-filtering）**架构，避免先检索后鉴权导致的查全率问题。
3. **上下文透传预留**：API 层需统一解析请求中的用户身份标识（如 `user_id`），并封装为 `UserContext` 向下透传，当前仅用于日志与 Trace 落表，暂不执行业务阻断。

#### 9.7.3 当前明确不做的内容
1. 坚决不在本系统中建设独立的权限管理后台、角色分配页面或用户树结构。
2. 坚决不编写复杂的权限计算逻辑，V1 阶段 `filters` 参数保持最小可用或为空。

#### 9.7.4 当前默认行为

当前阶段，系统默认采用最小权限预留策略：

1. 默认不在业务链路中执行复杂权限阻断。
2. 默认以单租户或基础隔离方式运行。
3. `UserContext` 当前主要用于日志、Trace 与后续扩展预留。
4. `filters` 参数当前可保持为空或最小可用状态。

结论：

**当前权限相关设计仅做接口预留，不作为当前主链路复杂度来源。**

### 9.8 当前支撑性链路的总体结论

当前阶段，在线问答主链路之外，只补充以下最小支撑能力：

1. 轻量离线数据入库
2. 高频 FAQ 缓存拦截
3. 基础安全拒答边界
4. 轻量反馈回流落表
5. 固定提问范式与输入引导
6. 核心 Prompt 与阈值的配置化管理
7. 数据隔离与前置过滤权限接口预留

这七类能力的共同目标是：

- 补齐系统闭环
- 降低重复计算
- 控制基本风险
- 降低输入随机性
- 为后续优化提供真实数据

一句话概括就是：

**当前阶段只补最小必要支撑链路，不引入新的重型架构中心。**

## 10. 当前目录与工程组织原则

### 10.1 当前目录组织原则

当前目录结构应围绕主链路，而不是围绕宏大架构概念。

目录组织原则如下：

1. 按当前职责组织
2. 不为未来预建大量层次
3. 命名以当前实现为准
4. 目录数量适度收敛

### 10.2 当前工程组织建议

当前建议围绕以下真实模块组织代码：

- api
- services
- retrieval
- routing
- storage
- frontend pages/components

如无真实复杂度，不建议再引入以下人为层次：

- graph orchestration
- agent runtime
- unified intent platform
- knowledge middleware framework wrapper

---

### 10.3 本地开发与 Vibe Coding 体验约束

当前阶段，系统除保证运行时主链路稳定外，还应明确保证最小本地开发体验，降低新成员接入阻力与试错成本。

#### 10.3.1 一秒启动的本地开发体验

当前阶段应支持最小 Demo 模式，保证开发者在无外部服务依赖的条件下快速启动并看到完整闭环。

当前建议至少满足以下要求：

1. 启动脚本或主入口支持 `--demo` 模式。
2. 开发环境支持 SQLite `:memory:` 或纯文件检索模式。
3. 启动 Demo 模式时，不要求安装 PostgreSQL、Redis、Docker 或其他外部服务。
4. 项目内应自带最小 mock 数据，例如 `mock_faq.json`，启动时可自动加载。
5. 开发者应能在最短路径内完成一次“提问 -> 检索 -> 回答 -> 展示”的闭环。

#### 10.3.2 开发态热重载与即时反馈

当前阶段应尽量减少“改一点配置就必须整服务重启”的挫败感。

当前建议至少满足以下要求：

1. 开发态下，`prompts/` 目录中的 Prompt 文件支持热重载或最小重载机制。
2. 修改 Prompt 后，不应要求开发者手工重启完整后端服务。
3. 前端开发服务器应尽量直接代理到本地 Python 后端，避免引入复杂反向代理链路。
4. 代码或配置变更后的反馈路径应尽量缩短到“保存 -> 刷新 -> 看到结果”。

#### 10.3.3 可视化调试与最小 Debug Overlay

当前阶段应为开发者提供最低限度的可视化调试能力，降低仅靠日志排错的认知负担。

当前建议至少满足以下要求：

1. 前端提供可切换的 Debug 模式。
2. Debug 模式下可展示最小链路信息，例如：
   - `normalized_query`
   - `route_result`
   - `router_used`
   - `retrieved_chunks`
   - `final_prompt`
   - `fallback_reason`
3. Debug 信息应服务于开发理解，不要求建设独立调试平台。

#### 10.3.4 可复制的调试上下文

当前阶段建议支持“一键复制当前调试上下文”，用于快速排错与沟通。

建议复制内容包括：

- `trace_id`
- `normalized_query`
- `route_result`
- `router_used`
- `retrieved_chunks`
- `final_prompt`
- `fallback_reason`

#### 10.3.5 一键回到已知可用状态

当前阶段建议提供最小环境重置能力，避免本地缓存、索引、配置残留影响开发判断。

建议至少支持：

1. 清空本地 demo 数据或缓存
2. 重建最小 mock 数据
3. 恢复到可运行的默认状态

结论：

**当前阶段的本地开发体验同样属于系统边界的一部分，应保证“易启动、易反馈、易调试、易恢复”，但不扩展为独立开发平台。**

#### 10.3.6 Demo / Dev / Prod 模式边界

为了避免开发便利性能力污染正式运行环境，当前阶段需要明确区分 Demo、Dev 与 Prod 三种模式的默认边界。

当前建议冻结如下：

- **Demo 模式**
  - 允许自动加载 `mock_faq.json` 或等价 mock 数据
  - 允许使用 SQLite `:memory:` 或纯文件检索
  - 允许展示最小调试信息
  - 目标是最短路径跑通“提问 -> 检索 -> 回答”闭环

- **Dev 模式**
  - 允许 Prompt 热重载
  - 允许 Debug Overlay
  - 允许记录最小调试字段，如 `normalized_query`、`retrieved_chunks`、`final_prompt`
  - 目标是缩短修改后的反馈路径

- **Prod 模式**
  - 默认关闭 mock 数据自动加载
  - 默认关闭 Debug Overlay
  - 不默认记录完整 `final_prompt`，如需记录应采用脱敏、摘要或显式开关方式
  - 目标是保证稳定性、最小暴露面与可控运行

结论：

**当前开发便利性能力必须受运行模式约束，不得默认泄漏到正式环境。**

#### 10.3.7 本地最小 Smoke Cases
  
  当前阶段建议维护一组极小的本地冒烟样例，用于在修改 Prompt、路由、缓存或检索逻辑后快速验证主链路是否仍可用。
  
  当前建议至少覆盖以下场景：
  
  1. FAQ 直接命中
  2. FAQ 缓存命中
  3. 路由低置信度进入 fallback
  4. 基础安全拒答
  5. 检索弱命中后拒答或 fallback
  6. 固定提问范式输入命中标准问答路径
  
  当前阶段不要求建设正式 benchmark 平台，但要求开发者在关键修改后能通过最小样例集快速判断：
  
  - 主链路是否还能跑通
  - 行为是否出现明显退化
  - 配置修改是否产生非预期影响
  
  当前阶段建议将本地 Smoke Cases 控制在少量核心样例范围内，优先覆盖：
  
  - 主链路可用性
  - 基础安全拒答
  - 路由 fallback
  - 检索弱命中边界
  - 固定提问范式命中
  
  当前阶段不要求把 Smoke Cases 扩展为完整测试矩阵，也不要求覆盖所有边缘输入。
  
  其目标是提供最小回归保护，而不是替代正式测试体系。

结论：

**当前本地 Smoke Cases 只作为最小回归保护带，不扩展为重型测试平台。**

#### 10.3.8 Debug 信息隔离与会话无状态边界

当前阶段在提供开发便利性时，必须同时保证调试信息隔离与后端无状态边界清晰。

##### （1）Debug 信息隔离

所有调试信息应通过独立的 `debug_info` 字段下发，而不与标准回答字段混合。

当前阶段要求：

1. Demo / Dev 模式下，允许下发最小调试信息，例如 `normalized_query`、`retrieved_chunks`、`final_prompt`、`fallback_reason`。
2. Prod 模式下，后端 API 层必须默认物理剔除 `debug_info`，而不是仅在前端隐藏。
3. 如确需在非开发环境中保留部分调试能力，应采用显式开关、脱敏或摘要方式处理。

##### （2）会话无状态边界

当前阶段虽然允许存在 `session_id` 与请求记录，但后端默认保持无状态处理，不自动将历史对话注入路由层与检索层。

当前阶段要求：

1. 路由层与检索层默认只处理当前请求输入。
2. 不自动拼接历史多轮对话，不引入隐式短期记忆。
3. 如需支持极简多轮，应由前端显式将必要上下文拼接到 `raw_query`，后端仍保持当前主链路无状态。

结论：

**当前阶段既要保证开发态调试体验，也要保证正式环境中的调试信息最小暴露；同时，后端默认保持无状态，以维持薄路由与轻检索架构的稳定性。**

## 11. 后续允许升级设计的触发条件

当前阶段不主动升级架构。只有在以下条件真实出现时，才考虑进入下一轮设计：

### 11.1 考虑引入图执行框架的触发条件

只有当以下情况明确出现时，才重新评估 LangGraph 或类似方案：

1. 出现真实多分支长链路业务流程
2. 明确需要状态持久化与恢复
3. 明确需要人工审核插点
4. 明确需要跨多个工具的稳定编排
5. 普通服务调用链已无法维持可维护性

### 11.2 考虑引入知识框架的触发条件

只有当以下情况明确出现时，才重新评估 LlamaIndex 或类似方案：

1. 文档来源快速增多
2. 检索类型显著复杂化
3. 节点组织、引用组织需求显著上升
4. 自研轻量检索维护成本显著高于引入框架成本

### 11.3 考虑升级意图层的触发条件

只有当以下情况明确出现时，才重新评估更强的意图解析层：

1. FAQ 之外出现第二个稳定业务场景
2. 需要在多个明确场景间做稳定路由
3. 当前规则 + 轻模型分类已明显不足
4. 已具备更强模型或稳定外部推理能力
5. 当前系统确实需要更强决策层，而不是想象中的未来扩展

## 12. 当前阶段结论

当前阶段，OrionStack 的正确设计方向不是继续增加框架层，而是继续收缩系统复杂度。

当前阶段的核心结论如下：

1. 系统聚焦 FAQ / 业务知识问答单一主场景
2. 主链路固定为“提问 -> 路由判断（薄） -> 检索 -> 回答 -> 返回”
3. 当前不引入 LangGraph
4. 当前不引入 LlamaIndex
5. 当前不建设重型统一意图层
6. 当前小模型只承担简单分类或回答生成职责
7. 当前只保留最小必要接口边界
8. 当前系统优先目标是稳定、可控、易维护
9. 当前系统除保证运行时主链路稳定外，也应保证本地开发体验低阻力、可快速反馈、可最小可视化调试。

一句话总结就是：

**先把当前问答主链路做薄、做稳、做可替换，同时保证本地开发过程可快速启动、可快速反馈、可快速定位问题，不把未来复杂系统的负担提前压到今天的实现里。**
